# 01 · 数据模型与字段定义

> 来源：`src/core/documentSchema.js`、`src/core/migrations.js`、`src/core/transactionMetadata.js` 实际实现 + 飞书实机结构对照。
> 目标：让「落库什么字段、每个字段什么含义」有唯一权威说明，避免正文与元数据互相污染。

---

## 1. 设计原则（三条铁律）

1. **正文与外壳分离**：Tiptap JSON 只存「正文」；`documentId` / `revisionId` / `schemaVersion` / 评论线程 / 在线状态**绝不混入正文**。
2. **同份 JSON 可投影**：同一份正文 JSON 既能被本地 Provider 直接存，也能被协同 Provider 投影到 `Y.Doc`，互不冲突。
3. **读取兼容、写入规范**：读时能兼容旧格式（`{title, json}`），写时统一走版本化信封。

---

## 2. 文档信封（DocumentRecord）

落库 / 传输的顶层结构，由 `createDocumentRecord()` 生成。

```js
{
  documentId:    string | null,   // 文档唯一 ID；null = 尚未分配
  schemaVersion: number,          // 外壳结构版本，当前 = 1
  revisionId:    string | null,   // 服务端修订版本；本地草稿为 null
  content:       DocNode,         // Tiptap doc 节点（正文）
  title:         string,          // 文档标题，空串而非 undefined
  updatedAt:     number           // 毫秒时间戳（Date.now()）
}
```

| 字段 | 类型 | 必填 | 含义 | 边界与约定 |
| --- | --- | --- | --- | --- |
| `documentId` | `string \| null` | 是 | 文档身份主键 | 未分配时为 `null`；赋值时强制 `String()` |
| `schemaVersion` | `number` | 是 | 外壳结构版本 | 非法值回落 `DOCUMENT_SCHEMA_VERSION`（=1） |
| `revisionId` | `string \| null` | 是 | 服务端 revision | 本地草稿 `null`；用于协同/版本比对 |
| `content` | `DocNode` | 是 | 正文根节点 | 必须 `type === 'doc'`；默认 `{type:'doc',content:[{type:'paragraph'}]}` |
| `title` | `string` | 是 | 标题 | 非 string 时回落 `''`（**不用 undefined**） |
| `updatedAt` | `number` | 是 | 更新时间戳（ms） | 非法回落 `Date.now()` |

### 2.1 兼容读取（`normalizeDocumentRecord`）

旧格式兼容规则：

| 输入形态 | 处理 |
| --- | --- |
| `{ content: DocNode }` | 直接用 `content` |
| `{ json: DocNode }` | 取 `json`（旧工作区格式） |
| `{ document: DocNode }` | 取 `document`（导出格式） |
| 三者都没有 / `type !== 'doc'` | **抛错** `文档记录缺少有效正文` |

```js
// ✅ 三种写法都合法
normalizeDocumentRecord({ title: 'A', json: doc })
normalizeDocumentRecord({ title: 'A', content: doc })
normalizeDocumentRecord({ title: 'A', document: doc })

// ❌ 抛错
normalizeDocumentRecord({ title: 'A' })
```

### 2.2 只取正文

```js
getDocumentContent(record)  // → DocNode，内部走 normalize
```

## 3. 节点 ID（评论 / AI 锚点）

```js
getNodeId(node)  // → string | null
```

| 规则 | 说明 |
| --- | --- |
| 读取路径 | `node.attrs.id` |
| 有效判定 | 必须是**非空字符串** |
| 缺失处理 | 返回 `null`，**绝不强行注入未知属性** |

> **为什么重要**：评论和 AI 结果要长期锚定到某个块。旧 Schema 没有 `id` 属性，此时返回 `null` 等待 Schema 迁移补上，而不是在运行时给节点硬塞字段（会污染 diff 和协同合并）。

## 4. 飞书实机块字段对照

飞书 DOM 上每个块携带的 `data-*` 属性（实机采集），是复刻时的元数据参考：

| 飞书属性 | 含义 | 示例 |
| --- | --- | --- |
| `data-block-id` | **创建期单调计数器**（详见下方 🔴 定案）。跨加载稳定，但**删块留洞不复用、插入不回填不重排** → 可作持久化键，**不可用来排序** | `219` |
| `data-block-type` | 块类型标识 | `text` / `heading1` / `table` / `table_cell` / `isv` / `page` |
| **`data-record-id`** | **第二套 ID**，22 位 base58。块根 **21/21 全带**。飞书内部 record 层标识（推断：同步块 / 评论 / 操作日志的锚点），**与 `data-block-id` 不是同一套** | `KI9edbwYPoeTcBxsIlDckbCbnIf` |

> ⛔ **块根 `data-*` 只有这 3 个**（batch276 A2 实测 21/21）。**没有 `data-block-align`** —— 旧记那条「推测」已删除；对齐信息在行内样式 / mark attrs 上，不在块根 data-* 上。

> 🔴 **`data-block-id` 语义定案（2026-10-25 batch277/278/279 实测，推翻「块自身固有 ID」的模糊表述）**：
>
> **结论：`data-block-id` = 「创建期单调计数器」（creation-time monotonic counter）**，不是文档序号、不是位置序号。
>
> | 事实 | 证据 |
> | --- | --- |
> | **删块留洞、id 不复用** | 全文普查（batch279）：**143 块**却占到 bid **1 → 253**，**缺号 110 个**（如 138–161、167–182 连续缺口） |
> | **插入不回填、不重排** | batch278 A2：在 bid=6 后插入内容，新块拿到 **bid 91 / 162–166**；而这些块**在文档顺序上夹在 91–129 之间**却持有更大的 id |
> | **跨加载稳定** | batch277 A3：12/12 文本块 bid **与** rid 两次加载**完全一致**（`bid 不一致 = []` / `rid 不一致 = []`） |
>
> **对实现的 3 条约束**：
> 1. ✅ bid **可以**做折叠状态 / 评论锚点 / 选区恢复的持久化 key（稳定 + 唯一 + 不复用）；
> 2. ⛔ bid **不能**用来排序 —— 文档顺序必须另取（DOM 顺序或服务端 `children` 数组）；
> 3. 建议 `nextBlockId = max(existing) + 1`，删除只标记不回收，**永不复用空洞**。
>
> 这正是折叠状态能按 `blockId` 持久化的前提（见 [09 §5.7.5-①](./09-开发方案-0.12.md)）。

> **旧结论留痕（batch269）**：当时用「两次加载 13/19 一致 + 6 处空块错位」推出「id 是块自身固有 ID」。**方向对了但不够精确** —— 真正的机制是「计数器 + 留洞」，batch278/279 的插入实验才把它钉死。

### 4.2 表格的 block-id 树（batch218 实测，**每个 cell、cell 内每个段落都是独立 block**）

飞书把表格拆成**三层 block**，`data-block-id` 一路贯下去，且 **id 是按 DOM 顺序连续分配的**：

```
div.block.docx-table-block[data-block-id="144"]        ← 表 block（1 个）
├─ table
│  ├─ tr
│  │  ├─ td.block.docx-table_cell-block[data-block-id="169"]   ← cell block
│  │  │  └─ div.block.docx-text-block[data-block-id="170"]     ← cell 内的段落 block
│  │  ├─ td…[data-block-id="171"]  → div…[172]
│  │  └─ td…[data-block-id="173"]  → div…[174]
│  └─ tr
│     ├─ td…[175] → div…[176]
│     ├─ td…[177] → div…[178]
│     └─ td…[179] → div…[180]
```

实测（同一张 2 行 3 列表，标题行开着 → 克隆表 3 td + 主表 3 td，共 6 个 `td`）：

```json
[{"tag":"DIV","cls":"block docx-table-block","id":"144","top":388,"h":83},
 {"tag":"TD","cls":"block docx-table_cell-block table-cell-b","id":"169","top":388,"h":41},
 {"tag":"DIV","cls":"block docx-text-block isEmpty","id":"170","top":397,"h":23},
 {"tag":"TD",...,"id":"171"}, {"tag":"DIV",...,"id":"172"},
 {"tag":"TD",...,"id":"173"}, {"tag":"DIV",...,"id":"174"},
 {"tag":"TD",...,"id":"175","top":429,"h":40},
 {"tag":"DIV",...,"id":"176"}, {"tag":"TD",...,"id":"177"},
 {"tag":"DIV",...,"id":"178"}, {"tag":"TD",...,"id":"179"}]
```

| 结论 | 值 | 对 V1 的意义 |
| --- | --- | --- |
| `td` 本身带 `data-block-id` | ✅ 有（`169/171/173…`） | cell 是**可寻址的 block**，`getCell(blockId)` 的 `blockId` 可以直接用 cell 自己的 id，不必拼 `表id:r:c` |
| `td` 内段落也带 `data-block-id` | ✅ 有（`170/172…`，与 cell id 连号） | cell 里可以有**多个段落**，是真正的 `block+` 容器，不是「一个 text 字符串」 |
| 空 cell 内段落 | `docx-text-block **isEmpty**` | 空 cell ≠ 无段落；**永远有 1 个空段落占位**（否则光标无处落） |
| id 分配 | **文档内递增数字，按 DOM 序** | 插入新行/新列会消耗新的连续 id；**不要用 id 大小推断顺序**（合并/拆分后会乱） |
| 克隆表里的 td | 也有 `data-block-id`（`169/171/173` 那组） | 标题行开启时，**克隆表复用主表的 cell id**（同一批 block 被渲染两次）→ 采集时按 `data-block-id` 查会**命中 2 个**，必须再判 `closest('table').className` |

> 🔴 **采集/实现两条铁律**：
> ① **块寻址一律用 `data-block-id`，不要用 `document.querySelectorAll('.docx-table-block')[i]`** —— 表格是**虚拟化挂载**的，滚出视口就 unmount，`i` 会整体左移（batch217 就是这么 `idx gone` 的：枚举时有 `i=0/1/2`，滚回顶部后只剩 `i=0`）。
> ② 克隆表的 cell 与主表**共用同一批 id**，`querySelector('[data-block-id="169"]')` 会返回**第一个**（克隆表里那个，`top` 在表头行）。要拿主表的，用 `[data-block-id="169"]` 全部命中后**取 `getBoundingClientRect().top` 更大的那个**，或先 `el.closest('.sticky-row-wrapper') === null` 过滤。

飞书**行内字体色 / 背景色**用同一个 span 承载，两个通道互不覆盖（实测 batch135）：

| 语义 | 落在哪 | 值示例 |

### 7.1 事务元数据 `transactionMetadata.js`（源码实读，非飞书采集）

> 来源：`apps/lark-doc/src/core/transactionMetadata.js`（与 `apps/lark-doc-demo/` 同源同内容，1211 B）。
> 这是**我方实现**的 ProseMirror `Transaction.meta` 约定，**飞书侧没有对应公开契约**（飞书协同用 OT 增量 + `revision`，内部字段未暴露），因此本节只定义我方接口，不冒充飞书实测。

**常量**

| 导出 | 值 | 说明 |
| --- | --- | --- |
| `TRANSACTION_META_KEY` | `'larkDocTransaction'` | 挂在 `tr.getMeta()` / `tr.setMeta()` 上的键名，单键承载整个对象，避免与其他插件 meta 撞键 |

**`TRANSACTION_ORIGINS`（冻结对象，6 个来源）**

| 键 | 值 | 何时用 | 现有调用点 |
| --- | --- | --- | --- |
| `USER` | `'user'` | 本端键盘/鼠标输入（**默认值**：不传 `origin` 时即落此值） | Tiptap 常规输入，不显式设置 |
| `REMOTE` | `'remote'` | 协同端推送的远端变更 | 协同 provider（预留） |
| `IMPORT` | `'import'` | 导入 md/html/docx 等外部内容 | 导入链路（预留） |
| `RESTORE` | `'restore'` | 快照 / 版本回滚 | 版本恢复（预留） |
| `AI` | `'ai'` | AI 提案写入（需与用户输入区分，便于「拒绝 AI 改动」） | AI 层（预留） |
| `HOST` | `'host'` | 宿主用 `setContent` / 模板整体替换正文 | `LarkDocEditor.vue:343`（`setContent` → `replaceWith` → dispatch） |

**`setTransactionMetadata(transaction, metadata?)` 写入的 5 个字段**

| 字段 | 类型 | 缺省 | 归一化规则 | 含义 |
| --- | --- | --- | --- | --- |
| `origin` | `string` | `'user'` | `metadata.origin \|\| TRANSACTION_ORIGINS.USER`（**空串也回退到 `user`**） | 事务来源，取 `TRANSACTION_ORIGINS` 六值之一 |
| `actorId` | `string \| null` | `null` | `== null ? null : String(...)`（数字会转字符串） | 操作者 id（用户 / 机器人 / 宿主会话） |
| `requestId` | `string \| null` | `null` | 同上 | 请求幂等键，用于「同一次网络请求只落一次」 |
| `baseRevision` | `string \| null` | `null` | 同上 | 该事务基于的文档修订号，协同冲突判定用 |
| `timestamp` | `number` | `Date.now()` | `Number(metadata.timestamp) \|\| Date.now()`（**传 0 会被替换成当前时间**） | 毫秒时间戳 |

**行为契约（3 条硬约束）**

1. **空值安全**：`transaction` 为假值或没有 `setMeta` 方法时**原样返回**，不抛错 → 可以安全地在没有编辑器上下文的纯数据层调用。
2. **不合并、不继承**：每次调用都**新建**一个完整对象覆盖 meta，不做浅合并。所以调用方想保留上次的 `actorId` 必须自己带上。
3. **`getTransactionMetadata(tr)` 只做类型校验**：非对象一律返回 `null`，不补默认值 → 「未写过 meta」与「写了空对象」在读取侧**都表现为 `null`**，消费方必须自己兜 `origin` 默认值。

**典型用法**

```js
// 宿主整体替换正文（LarkDocEditor.vue setContent 路径）
const tr = editor.state.tr.replaceWith(0, editor.state.doc.content.size, next.content)
editor.view.dispatch(setTransactionMetadata(tr, { origin: TRANSACTION_ORIGINS.HOST }))

// DocumentSession 统一入口：来源 + 请求幂等键 + 基线修订
session.dispatch(tr, { origin: TRANSACTION_ORIGINS.REMOTE, actorId: 'u_123', requestId: 'req_abc', baseRevision: '17' })
```

> 🔴 **V1 实现注意**：`origin` 只影响**历史分组与审计**，不改变文档内容。若宿主希望「AI 写入不进 undo 栈」，需要在 dispatch 前自己包 `closeHistory`，**不要**指望 `origin: 'ai'` 自动生效 —— 当前实现没有任何按 origin 分流的历史策略。
