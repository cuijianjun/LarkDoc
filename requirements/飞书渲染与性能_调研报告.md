# 飞书渲染引擎与文档性能 —— 调研报告

> 调研目的：回答两个问题 ——（1）飞书**到底在哪里**用了 Canvas 渲染引擎；（2）飞书文档的**性能是怎么保证的**。
> 落脚点：我们（`apps/lark-doc`，Vue 2.7 + Tiptap 3 / ProseMirror，DOM 渲染）该学什么、不该学什么。
> 调研日期：2026-10-24　｜　一手材料：`~/codex/飞书文档网页编辑器_需求文档.md`（31,403 行）+ 外网取证

---

## 0. 结论先行（TL;DR）

| 问题 | 结论 |
| --- | --- |
| 飞书**文档正文**用 Canvas 吗？ | **不用。** 是 **DOM + `contenteditable` 块树**（三重独立证据互证） |
| 那 Canvas 用在哪？ | **三处**：① Sheet 电子表格（自研 Canvas）② Bitable 多维表格（自研 Widget 引擎 → Canvas，参考 Flutter）③ 画板 / 白板（`whiteboad-x-canvas-container`，本地实机抓到）。另外 MindNote 思维笔记用 **SVG** |
| 核心设计哲学 | **协同算法可以统一，渲染层必须按场景定制**。飞书不是一个渲染引擎打天下，而是 Doc/Sheet/Bitable/MindNote 四套渲染层 |
| 性能靠什么保证 | 不是靠"用 Canvas 更快"，而是：**块树数据模型 + OT 协同粒度 + 脏矩形/离屏/批量渲染 + FVG 直出 hydrate + Awareness/评论/存储三路解耦 + 乐观更新与增量渲染** |
| 我们该学什么 | 学**架构分层与解耦**（块树、命令注册表、装饰不写正文、懒加载、通道分离）；**不要**为了"像飞书"把正文改成 Canvas |

## 1. 飞书在哪里用了 Canvas —— 逐场景拆解

### 1.1 四类文档、四套渲染层

| 产品 | 渲染层 | 为什么这么选 | 证据来源 |
| --- | --- | --- | --- |
| **Doc（文档）** | **DOM** | 富文本天然适合 DOM：IME 输入法、文本选区、Ctrl+F 浏览器搜索、无障碍/读屏、复制粘贴全部免费获得 | 本地需求文档 21.7 实机 DOM 树；知乎实机拆解；腾讯云架构文对照表 |
| **Sheet（电子表格）** | **自研 Canvas** | 百万级单元格，DOM 节点数爆炸；表格是规则网格，包围盒可全当矩形处理，命中检测简单 | 知乎实机拆解「表格用了自研 Canvas 进行绘制」 |
| **Bitable（多维表格）** | **自研 Widget 引擎 → Canvas**（对齐 Flutter） | 视图形态多（表格/看板/日历/画廊），需要声明式布局；用 Widget 树 + Flex 布局统一描述 | 《浅谈 Canvas 渲染引擎设计》长文 |
| **MindNote（思维笔记）** | **SVG** | 节点少、连线多、需要矢量缩放与 DOM 事件 | 同上 |
| **画板 / 白板（Board）** | **Canvas**（`whiteboad-x-canvas-container`） | 自由绘制、无限画布、图形量大 | **本地需求文档实机抓取**（见 1.3） |

### 1.2 文档正文是 DOM 的三重证据

**证据 A —— 本地需求文档第 21 章（逆向实机采集，2026-10-23）**

正文编辑区的真实 DOM 结构：

```
div.page-block.root-block            ← 根块，contenteditable
  └ div.page-main-item.editor
      └ div.editor-container
          ├ div.zone-container.text-editor        （空块）
          └ div.zone-container.text-editor.non-empty  （非空块）
```

关键观察：
- 每个块自带 `zone-container text-editor`，**各自 `contenteditable`** —— 典型的「块树 + 每块独立编辑区」架构
- 公式 / 缩写 / @提及是**插件化**注入：`editor-kit-plugin-*`、`editor-kit-*-popover-wrapper`
- 全文 `contenteditable` 命中 **22 处**，而 `canvas` 只命中 **8 处且全部集中在画板**

**证据 B —— 知乎一手实机拆解原文**

> 「飞书文档 Doc 还是用的 DOM，表格用了自研 Canvas 进行绘制。」

**证据 C —— 腾讯云开发者社区架构文对照表**

> Doc（文档）→ DOM → 「富文本场景天然适合 DOM，IME 输入、辅助功能成熟」

### 1.3 Canvas 的实机证据（画板 / 白板）

本地需求文档 30878–30933 行，实机抓到的画板 DOM 树：

```
div._container-C6QEwr.whiteboard-canvas-container
  └ div.whiteboad-x-app.whiteboad-x-canvasInputEventTarget   tabindex=0
      ├ div.whiteboad-x-canvas-container       ← 真正画布，渲染层挂这里
      └ input.whiteboad-x-canvas-input.ratio-text-input
```

> ⚠️ 注意类名拼写 `whiteboad`（**少一个 `r`**），是飞书线上既有 bug。本地需求文档已注明「复刻应保持一致以便兼容选择器」。

另有一处 `canvas_size_relative_parent`（尺寸测量宿主）与空画布占位 `empty-canvas-placeholder-text`。

**结论**：我们这个项目只有在**复刻画板/白板**时才需要真正引入 Canvas；正文、表格块（Tiptap 表格）都不需要。

补充：本地需求文档 13833 行还提到表格的 **「图片导出/复制的离屏渲染服务」**（含空白行列裁剪、飞书淡蓝边框）——即 Sheet 有一个"离屏画布快照渲染管线"，用于「复制为图片 / 下载为图片」。这是 Canvas 的第四处轻量用法（离屏导出，非交互渲染）。

## 2. 飞书文档的性能是怎么保证的

按**四层**拆开看，性能从来不是单点优化，而是全链路分层。

### 2.1 数据模型层：块树（Block Tree）

文档 = 以 `page` 为根的 **Block 树**，30+ Block 类型（文本类 / 容器类 / 嵌入类 / 媒体类 / 装饰类）。

```json
{
  "block_id": "...",
  "block_type": "text",
  "parent_id": "...",
  "children": ["..."],
  "comment_ids": ["..."],
  "text": { "elements": [{ "text_run": { "content": "...", "text_element_style": {} } }] }
}
```

**为什么这是性能地基**：
- 协同/持久化的最小单位是 **Block**，不是整篇文档 → 增量同步、增量渲染才有落脚点
- 大纲、目录、评论、折叠全部是块树的派生视图，不需要扫描正文
- 评论挂在 Block 的 `comment_ids` 上 → **评论与正文解耦**，删块时评论"已失效但保留"

> 对应到我们：ProseMirror 的 doc 本身就已经是块树（node = block）。这块我们**天然具备**，不用改。

### 2.2 协同层：OT + 乐观更新

- 飞书走 **OT**（自研 Couper，强中心化），编辑器内核自研 **Bear**；CRDT（Yjs）是另一条路线
- **乐观更新**：本地先改，不等服务端往返 → 输入零延迟（本地需求文档 8 章同样规定「输入反馈不得等待持久化往返」）
- **本地缓冲队列（IndexedDB）** + 向量时钟/版本号 + **指数退避重连**
- **增量渲染**：远端 Op 应用后只重绘受影响块，非全量重绘
- **Awareness 独立通道**：光标位置 / 在线状态这类高频、可丢包的数据，与正文 Op **分通道传输**，不互相阻塞
- 存储分层：元数据 MySQL / 操作日志 Mongo / 快照对象存储 / 会话 Redis / 检索 ES；读写分离 + 文档分片

### 2.3 渲染层：Canvas 引擎的六项关键手段（Sheet / Bitable）

| # | 手段 | 飞书怎么做 | 关键点 |
| --- | --- | --- | --- |
| 1 | **脏矩形 / 脏区渲染** | 计算改动前后的包围盒 → 多个脏区按**相交面积优先合并** → 剩余 >5 个继续合并到 5 → 依次 `clearRect` + `clip` 局部重绘 | 这是飞书多维表格性能最好的关键；飞书**没有做 Canvas 分层**，纯靠脏矩形撑住 |
| 2 | **离屏渲染 + 虚拟列表 Widget** | 虚拟列表 Widget 支持 `key` diff，滚动时**回收 / 创建 / 复用**节点，可复用部分走离屏渲染 | 对比 Konva：Konva 是 Group 级 `cache()`，且因用色值法要画 4 份（主/hit/cache/cacheHit）；飞书是**列表级**，粒度更贴合业务 |
| 3 | **异步批量渲染** | `batchDraw()` 用 `requestAnimationFrame` 合并到下一帧统一绘制（等价于 React 的 `setState` 批处理） | Konva 与飞书 Bitable 都支持 |
| 4 | **事件命中检测（几何法）** | 包围盒建 **R Tree** 空间索引 → 按 z-index 找最顶层 → 射线法判奇偶交点 | 表格业务里所有元素**可全当矩形**（AABB），飞书因此比通用方案简单很多；Konva 用**取色值法**（随机 colorKey + hitCanvas + `getImageData`，精度高但要画两份，且 `getImageData` 在高频 wheel 场景掉帧） |
| 5 | **FVG 格式 + 服务端直出 hydrate** | Widget 可「脱水」成 FVG 数据结构；服务端**直出已过排版计算**的 Widget 数据，JS 加载完直接 FVG → Widget → Canvas | 原链路「拉数据 → 加载资源 → 反序列化 → 初始化 Model → 排版 → 渲染」被砍成「拉数据 → FVG → 渲染」，**接近 React hydrate**，省掉反序列化/初始化/排版三阶段 |
| 6 | **Widget 引擎对齐 Flutter** | state 数据驱动；基础 Widget（richtext / text / icon）+ 布局 Widget（Column / Row / Flex / Expanded / Margin / Padding / GridView），底层实现**一套 Flex 布局** | 声明式描述视图，视图形态（表格/看板/日历/画廊）切换只是换 Widget 树 |

### 2.4 工程层：官方容量与规模口径

飞书帮助中心《文档常见上限》（官方口径）：

| 项 | 上限 |
| --- | --- |
| 单文档 Block 数 | **40,000**（新版；旧版口径为 50 万字符） |
| 单个 Block 字符数 | **100,000** |
| 同时编辑人数 | 200 |
| 同时阅读人数 | 5,000 |
| 单文档表格数 | 300 |
| 单文档图片数 | 1,000（单图 ≤ 20MB） |
| 导出体积 | ≤ 100MB |

> 对照：本地需求文档 13.17 把「2,000 块 / 2MB 文本」定为**项目建议基线**（明确标注非飞书指标）。差距 20 倍，说明我们的目标量级远小于飞书，不必过早引入重型优化。

### 2.5 一个可借鉴的旁证：飞书开源 RTV（RichTextVista）

鸿蒙生态首个深度集成**属性字符串（StyledString / AttributedString）**的富文本组件：
- 摒弃基于 Component 的路径，**减少视图层级**
- 万级消息长列表 **120 FPS**
- 已在飞书 IM / 日历 / 云文档 / 视频会议等 **8 个核心模块**稳定运行半年以上

启发：**减少视图层级**是跨端富文本性能的通用解法（鸿蒙上靠属性字符串，Web 上等价于减少 DOM 嵌套 + 用装饰而非真实节点）。

## 3. 我们需要怎么学 —— 落地建议（分级）

### ✅ P0：直接对齐，成本低收益高

| 项 | 飞书做法 | 我们在 lark-doc 怎么落 |
| --- | --- | --- |
| **块级架构** | 一切皆 Block，派生视图（大纲/评论/折叠）读块树 | ProseMirror doc 已是块树，**保持**：大纲、折叠、编号都从 doc 派生，不另建模型 |
| **装饰不写正文** | 编号/高亮是渲染层产物，不进内容模型 | 已在做（标题编号现算不落正文、折叠键用 blockId）——**继续坚持**，这是对的 |
| **命令注册表** | 浮动工具栏 `text-toolbar` 12 项，每项有 `data-name` 命令 id；块手柄 13 项菜单、顶栏更多 27 项、编号菜单 3 项 | 把工具栏 / 气泡条 / 块菜单 / 快捷键统一到一个**命令 id 注册表**，避免"同功能多份实现"（历史上标题菜单分叉过 152/32/蓝字三个版本，就是没注册表） |
| **重量依赖懒加载** | 按需加载 | mermaid / katex / docx / mammoth 已懒加载 —— 保持 |
| **输入不等待持久化** | 乐观更新 + 本地缓冲 | 本地版已用 IndexedDB；**只在本地事务提交成功后才显示"已保存"** |
| **增量渲染** | 远端 Op 只重绘受影响块 | ProseMirror 本身按 transaction 做最小 DOM diff，已具备；**别在 dispatch 外手动整树刷新** |

### 🟡 P1：中期考虑，需要实测数据支撑

| 项 | 说明 |
| --- | --- |
| **长文档按需渲染 / 视口裁剪** | ProseMirror 默认全量 DOM。本地基线 2,000 块 / 2MB。建议**先实测**（2000 块文档的输入延迟、滚动 FPS、首屏时间），只有实测不达标才上虚拟化；过早优化会破坏浏览器搜索、选区、打印 |
| **Awareness 与正文分通道** | 若上协同（Yjs），光标/在线状态走 Awareness，**绝不与正文更新同通道** |
| **评论与正文解耦** | Block 挂 `comment_ids`，删块时评论转"已失效"而非级联删除 |
| **减少 DOM 层级** | 借鉴 RTV 思路：装饰节点用 CSS `::before` / Decoration Widget，不新增真实 DOM 层级 |
| **批量渲染** | 高频装饰更新（折叠/高亮/hover）用 `requestAnimationFrame` 合并，避免一次输入触发 N 次重排 |

### 🔵 P2：**实现不抄，但思想要学**（原判「不用学」已修正）

上一版把下面三项归为「不用学」，那是按「要不要抄实现」分的；按「要不要学思想」重评，结论不同：

| 技术 | 抄实现的代价 | 我们是否具备前提 | 可迁移的思想 | 落地方式 |
| --- | --- | --- | --- | --- |
| **脏矩形渲染** | 大（需整套 Canvas 渲染层 + 视觉回归） | ❌ 正文是 DOM，没有 Canvas 渲染层 | 「只更新变化区域，不全量重算」 | 用它审我们自己的**装饰层**：折叠高亮 / 标题编号 / overlay 是否每次 transaction 都全量重算？改成只重算受影响块 ≈ 150 行 |
| **离屏渲染** | 大 | ❌ | 「先在不可见处构建，再一次性挂上」 | DOM 等价物：`DocumentFragment` 批量插入、`content-visibility: auto`、先 `display:none` 构建再显示 |
| **R Tree 命中检测** | 中 | ❌ DOM 自带命中测试，不需要 | 「用空间索引避免全量遍历」 | 只有在大表格 / 虚拟列表里做 `getBoundingClientRect` 全量扫描时才需要；bucket 或二分即可，不必真上 R Tree |
| **FVG 直出 hydrate** | 中 | ✅ **有前提，且已半实现** | 「持久化**已计算过**的状态，别存原始串再重算」 | 我们落库是 ProseMirror JSON（已是结构化直出，优于存 HTML 再 parse）。下一步：把标题编号 / 大纲 / 折叠索引等**派生数据一起快照**，读档时跳过二次计算 |
| **自研 OT（Couper）** | 很大（transform 正确性 + 并发 fuzz） | ❌ Yjs 已解决 | 「中心化 vs 去中心化的取舍」 | 用 Yjs；但**要知道它的短板**：`y-websocket` 是**无权限广播模型**，权限 / 版本历史 / 快照压缩 / 审计都得自己补——别以为选了 Yjs 就万事大吉 |
| **自研编辑器内核（Bear）** | 极大（IME、选区映射、粘贴、schema） | ❌ 绝对不做 | — | ProseMirror |
| **存储分层 / 读写分离 / 分片** | **小**（是设计问题，不是代码量问题） | ✅ **本地版也有等价问题** | 「按访问模式拆分存储，别一个大 blob」 | IndexedDB 里把 **元数据 / 操作日志 / 快照 / 会话** 分表；目录列表只加载元数据不读全文；写走异步队列不阻塞读 |

### ❌ 明确不该学

| 项 | 为什么 |
| --- | --- |
| **把文档正文改成 Canvas** | 飞书自己正文也不用 Canvas。改成 Canvas 会丢：文本选区、IME 输入法、Ctrl+F 浏览器搜索、屏幕阅读器、原生复制粘贴、打印 —— 每一项都要自研补回，成本极高（知乎拆解里专门列了「用 Canvas 实现虚拟列表的四大难点」：排版（emoji 零宽连接符 / 冷门文字宽度）、无 DOM 事件、浏览器搜索失效、文本选区） |
| **自研渲染引擎** | 我们只有正文 + 表格块，ProseMirror + DOM 完全够 |
| **为了"像飞书"而复制其 bug** | 画板 `whiteboad` 少 `r` 的类名只在**复刻画板**时为兼容选择器才保留，其他地方不要模仿 bug |

### 💡 唯一建议上 Canvas 的场景

#### 3.5 修正：AI 编程是否改变上述判断？

不改变**价值排序**，但改变**可行性阈值**。三句话：

1. **AI 把「编写成本」压到接近 0，但没有压低「验证成本」。** 上面每一项最难的部分都不是写，是**证明它对**：OT/CRDT 要随机并发 fuzz 验收敛；脏矩形要视觉回归验不画花；存储要验崩溃恢复。AI 能帮你把测试写出来，但跑出来的 bug 仍要你理解为什么——代码量越大，这部分越贵。
2. **真正的判据没变：这项技术解决的是不是我们真实存在的瓶颈。** 没有 Canvas 渲染层 → 脏矩形解决不了任何问题，写了也是死代码。有 IndexedDB 大 blob → 存储分层立竿见影。
3. **反直觉的一点：AI 编程让「为学习而造轮子」变得划算了。** 本项目 README 明确定位「个人学习用途」，所以"造一遍只为搞懂原理"是有正当性的——前提是它**不进生产主包**。

**处置原则：区分「生产代码」与「学习 demo」**

| 轮子 | 规模 | 能搞懂什么 | 是否进 lark-doc 主包 |
| --- | --- | --- | --- |
| 脏矩形 Canvas demo（独立 HTML，格子随便点） | ~300 行 | 包围盒合并、`clip` 局部重绘 | ❌ 独立 demo |
| 简易 OT（只做 insert/delete + 双客户端模拟 + fuzz 断言收敛） | ~400 行 | transform 函数、为什么必须收敛 | ❌ 独立 demo |
| IndexedDB 分层存储（日志 + 快照 + 压缩合并） | ~300 行 | 增量持久化、崩溃恢复 | ✅ 可进（V2） |
| DOM 装饰的「脏区更新」（只重算受影响块） | ~150 行 | 脏矩形思想在 DOM 上的等价物 | ✅ 可进 |
