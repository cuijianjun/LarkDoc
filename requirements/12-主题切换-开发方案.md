## 4. 关键技术决策（含取舍）

### 4.1 D1 · 变量挂 `.lark-doc` 而非 `:root`

**采纳**。SDK 是嵌入式的，写 `:root` 会污染宿主页面。现状第 1 行已挂 `.lark-doc`，保持。

代价：宿主要覆盖只能在 `.lark-doc` 或其祖先上写（祖先可行，CSS 变量继承），或在 JS 里对根容器 `style.setProperty`。文档需写清。

### 4.2 D2 · 跨界 token 必须拆分（双轨的成败点）

**问题**：`--ld-border` 同时被菜单（chrome）和表格（content）引用。UI 深 + 正文浅时，它该取哪个？

**采纳方案：不共用，强制拆分**。

```
--ld-border-chrome    → [data-theme]        菜单/弹窗/工具栏/侧栏
--ld-border-content   → [data-content-theme] 表格/引用/callout/代码/分割线
```

同理拆：`--ld-bg-hover-chrome / --ld-bg-hover-content`、`--ld-shadow-chrome / --ld-shadow-content`。

代价：token 数从 24 涨到约 32。收益：双轨不会互相污染。**这是唯一能正确支持飞书「UI 深 + 正文浅」的做法。**

### 4.3 D3 · 不用 `light-dark()`

`light-dark()`（Baseline 2024）只认 `color-scheme` 这一**单维**属性，表达不了"UI 与正文各自独立"；且它要求 `color-scheme` 在祖先上，与 D1 的"只影响子树"有微妙冲突。**不采纳为主力**，仅在纯 chrome 且无双轨需求的少数处可考虑（首版一律不用，保持一致性）。

### 4.4 D4 · 收编一次性全量，不做渐进

渐进会留下"一半深一半浅"的中间态，**比全浅更难验收**。采纳：T0 一次性收编完（浅色视觉零变化），T2 再统一上深色。风险用"逐批截图 diff"对冲。

### 4.5 D5 · 色相不动，只做等价替换

T0 只做"字面色 → token"的**等价替换**，**不擅自改任何色相**（含绿蓝混用问题）。确保 `git diff` 后浅色视觉零变化可被截图证明。改色相单开任务，需你确认。

### 4.6 D6 · `theme` 默认值保持 `'light'`

改 `'system'` 会让现有宿主首屏突变深色，属于破坏性变更。**保持 `'light'`**，在 demo 里演示 `system`。

### 4.7 D7 · 跟宿主用「读属性 + 映射」，不用「读变量」

**采纳**。实测宿主 `pcvue-1023` **零 CSS 自定义属性**（全库 `*.scss` 中 `--xxx:` 命中数为 0），主题是 `@mixin useTheme` 编译期展开成 `html[data-skin="dark"] .foo {}` 的具体规则。

→ `var(--宿主变量)` 继承路线**不成立**。只能读 `documentElement[data-skin]` 属性 + 映射表。

代价：lark-doc 需持有一个 `hostSkin.map`，宿主加新皮肤时要同步。**换取的是零宿主改造量**（宿主不用为了 lark-doc 去引入 CSS 变量体系）。

### 4.8 D8 · 深色给两套档，不二选一

| 档 | 底色 | 适用 |
| --- | --- | --- |
| 默认档（中性灰 `#17181A`） | 通用 | 独立使用 / 其他宿主 |
| 宿主档（墨绿 `#1d3d39`） | pcvue | preset 引入覆盖，不改默认 |

理由：宿主深色是墨绿系，与中性灰并排会割裂；但把中性灰改成墨绿又会祸及其他宿主。**preset 覆盖是唯一不牺牲任何一方的做法**。
