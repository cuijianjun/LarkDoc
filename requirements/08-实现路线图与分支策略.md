## 3. 分支模型

### 3.1 拓扑

```text
master ───●───●───●──(0.11.6 hotfix)──●───────────────●──(0.12.0)──●──(0.12.x fix)
           \                          ↑               ↑
            \                    cherry-pick -x   一次 --no-ff 整期合并
             \                                        │
next/0.12 ────●───●───●───●───●───●───●───●───●───●───●───●───●──●──●
                       ↑       ↑       ↑       ↑       ↑       ↑
                  feat/p1-  feat/p2- feat/p3- feat/p4- feat/p5- feat/p6-
                  blocks   media    embed    inline   data     v2
```

### 3.2 七条规则

| # | 规则 | 理由 |
| --- | --- | --- |
| 1 | `master` **只接受** `fix/*` 与 `release/*`；功能一律进 `next/0.12` | 保证 0.11.x 用户拿到的永远是修好的稳定版 |
| 2 | 每期从 `next/0.12` 切 `feat/pN-xxx`，**合并回 next 用 `--no-ff`** | 保留每期的合并点，回滚按期粒度 |
| 3 | **每 3 天**（或每次 hotfix 合并后）跑一次 `next` 上 `git merge master` | 把大冲突摊成小冲突；方向**单向** |
| 4 | hotfix 若落点也在 next 上改过 → **`cherry-pick -x`**，不要 `merge master` | `-x` 记录来源 sha，日后好追 |
| 5 | 版本号：master `0.11.x`；next `0.12.0-beta.N`，**只发 npm `beta` dist-tag** | 否则 beta 会抢 `latest` |
| 6 | 每期收口打 `v0.12.x-beta.N` tag（在 next）；整期稳定才合 master 打 `v0.12.0` | beta 与正式版 tag 分离 |
| 7 | 合 master 前必须过 §7 的门禁（check + 三端 e2e + 断言基线 + size） | 不然等于把功能分支当 master 用 |

### 3.3 命令清单（可直接抄）

```bash
# ① 建长驻分支（一次性）
git checkout master && git pull
git checkout -b next/0.12 && git push -u origin next/0.12

# ② 开一期
git checkout next/0.12 && git pull
git checkout -b feat/p2-media

# ③ 收一期
git checkout next/0.12
git merge --no-ff feat/p2-media -m "feat(p2): 媒体与文件块"
git tag v0.12.2-beta.1 && git push origin next/0.12 v0.12.2-beta.1

# ④ master 修完 bug 回流 next（二选一）
git checkout next/0.12 && git merge master          # 冲突少时
git cherry-pick -x <fix-sha>                        # 只回一个修

# ⑤ 整期上正式版
git checkout master && git merge --no-ff next/0.12 && npm run ship -- --minor
```

### 3.4 发布脚本要先补的能力（P0 任务之一）

现状 `release.sh` 永远发 `latest`，且非 master 只 warn（`release.sh:162`）。P0 要加：

- `--tag beta`（传给 `npm publish --tag beta`）与 `--pre beta`（版本号生成 `0.12.0-beta.1`）；
- `BRANCH != master && !--tag` → **直接 die**（不再 warn），防止误发 latest；
- 校验环节 `latest` 断言在 `--tag beta` 时改为断言 `beta` 指向新版本。

## 5. 多框架方案

### 5.1 三条路线对比

| 方案 | 做法 | 改造成本 | 运行成本 | 风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A · element 统一运行时 | 全部框架都用 `<lark-doc>`，Vue 2 内联进产物 | 几乎为零（现状） | 包 +~90KB gz；无原生插槽/受控组件；SSR 必须 `dynamic(ssr:false)` | 低 | 短期可用，不能作为长期架构 |
| B · core + 全量去 Vue | UI chrome 全部改原生 DOM/TS，Vue 只剩可选壳 | 高（≈重写 14k 行 UI） | 最小，可做 Headless | 高，工期翻倍 | 长期目标，不在本轮 |
| **C · 混合（推荐）** | core 零框架 + chrome 仍 Vue 2 编 element + 三个薄适配 | 中（P0 一期） | 中（element 体积不变） | 中 | ✅ 本轮采用 |

### 5.2 方案 C 的模块边界

```text
lark-doc
├─ core/                  ← 零 Vue、零 UI。剩余功能 70% 落在这里
│   ├─ schema + blocks/   每块一个 Node extension
│   ├─ nodeviews/         纯 DOM class（不写 .vue）
│   ├─ serialization/     JSON / HTML / Markdown / Vditor 归一化
│   ├─ commands/          命令定义（12 分类，一分类一文件）
│   ├─ providers/         5 类契约
│   └─ policy/            网络/安全/限制
├─ ui-vue2/               ← 现有 SFC 全套（工具栏、气泡条、菜单、面板）
│   └─ 编成 dist/lark-doc-element.umd.min.js（inline-vue）
└─ adapters/
    ├─ vue2   → new LarkDoc(options) / <lark-doc-editor>
    ├─ vue3   → <lark-doc> 包装，props/emit/ref
    └─ react  → <LarkDoc ref>，useEffect 挂载，onChange 等事件
```

**核心判断**：剩余功能里，**块节点 + 序列化 + 命令 + 策略**是框架无关的（P1/P2/P3/P5 的主体），**面板与浮层 UI** 是框架相关的（P4 的一部分）。前者只写一次，后者只在 `ui-vue2` 写一次、三端共用同一 element → 不存在"三份实现"。

### 5.3 八条硬规则（写进 PR checklist）

1. 新增块类型 = `core/blocks/<name>.js` + 在 `registry/blocks.js` 加一行；**禁止**在 SFC 里写 schema。
2. NodeView 一律用 DOM class；**禁止**新增 `.vue` 的 NodeView（现有 2 个在 P0 迁完）。
3. `core/` 内不许出现 `vue` / `this.$set` / SFC 语法；ESLint 加 `no-restricted-imports` 拦 `vue`。
4. UI 面板只在 `ui-vue2` 实现一份；Vue 3 / React 通过 element 复用，不复制逻辑。
5. 适配层只做三件事：props → options、事件转发、方法代理；超过 150 行即视为业务泄漏。
6. CSS 只走类名 + CSS 变量（`--lark-doc-*`），不依赖宿主框架的 scoped 机制。
7. 宿主可见契约（属性/事件/方法）改动必须同步 `web-component/attributes.js` + `docs/guide/web-component.md`。
8. 每个新块必须带一份 `test/fixtures/blocks/<name>.json`，否则 CI 不通过。

### 5.4 三端能力矩阵

| 能力 | Vue 2.7 | Vue 3 | React 18/19 | 原生/CDN | SSR |
| --- | --- | --- | --- | --- | --- |
| 引入方式 | `new LarkDoc()` / SFC | `<lark-doc>` + 适配 | `<LarkDoc>` + 适配 | `<script>` | 客户端动态挂载 |
| 受控内容 | ✅ `v-model` / `content` | ⚠️ 属性 + `update` 事件（非受控） | ⚠️ 同上 | ⚠️ 设置属性 | — |
| 自定义工具栏 | ✅ `toolbar-keys` | ✅ 属性 | ✅ props | ✅ 属性 | — |
| 自定义 UI 插槽 | ✅ 组件 | ❌ | ❌ | ❌ | — |
| 包体积 | 复用宿主 Vue | +内联 Vue | +内联 Vue | — | — |

> 明确写进 README 的取舍：**非 Vue 2 宿主不接受自定义 UI 插槽**，只接受配置化（`toolbar-keys` / `toolbar-excludes` / `features`）。这是方案 C 的代价，比"三套 UI"便宜得多。

### 6.2 交接约定

- 每期开工前在 next 上打 `phase-pN-start` tag，方便对齐"从哪儿分叉"。
- 期与期之间**串行**（不建议并行两条 feat），除 P3/P4 可并行（都只加新文件、互不碰 core 注册表以外的文件）。
- 每周一次 `next` 上的 `git merge master` 由固定节奏执行，不做"攒着一起合"。
- 合并前 `git log --oneline master..next | wc -l` 超过 60 条就说明该收口了（避免长分支腐化）。
