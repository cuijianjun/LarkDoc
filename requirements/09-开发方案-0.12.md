1. **性能不是靠 Canvas，是靠分层解耦**——块树、装饰不写正文、通道分离、派生数据快照。这四条我们已经做对两条（块树天然具备、装饰不写正文），缺的是后两条。

## 2. 目标架构与硬边界

### 2.1 目录与依赖方向

```text
src/
├─ core/                    ← 零 Vue、零 DOM 依赖（唯一数据真相层）
│   ├─ schema.js            schema 装配（原 documentSchema.js 扩展）
│   ├─ blocks/<name>.js     24 → 52 种块，一块一文件
│   ├─ nodeviews/<name>.js  纯 DOM class（不许出现 .vue）
│   ├─ commands/<group>.js  12 分类，一分类一文件
│   ├─ serialization/       JSON / HTML / Markdown / Vditor
│   ├─ embed/               ← 新增：EmbedDef 注册表 / URL 解析 / 桥协议 / 卡片 schema（零网络）
│   └─ policy/              network / limits / security
├─ registry/                ← 唯一的"清单"层，只做 import + 汇总
│   ├─ blocks.js  commands.js  toolbar.js  panels.js  nodeviews.js  embeds.js
├─ session/                 ← DocumentSession（已存在，181 行）
├─ providers/               ← 5 类契约（已存在，117 行）
├─ components/lark-doc/     ← ui-vue2：SFC 全套（现状 8 个 .vue）
├─ web-component/           ← <lark-doc> 自定义元素（已存在，342 行）
├─ mount/                   ← Vue 2 渲染适配
└─ collab/                  ← 新增：Yjs 适配（唯一允许 import yjs 的地方）
```

**依赖方向（单向，违反即 CI 红）**：

```text
components/ ──→ registry/ ──→ core/
web-component/ ──→ mount/ ──→ components/
session/ ──→ providers/ ──→ core/
collab/ ──→ core/ + providers/        （core 不许反向 import collab）
core/embed/ ──→ core/                 （只解析 + 编解码，不发请求、不认识 provider）
```

### 2.2 十三条硬规则（进 PR checklist，CI 尽量机器化）

1. 新块 = `core/blocks/<name>.js` + `registry/blocks.js` 加一行 + `test/fixtures/blocks/<name>.json`。三者缺一，CI 不通过。
2. NodeView 一律 DOM class；**禁止**新增 `.vue` 的 NodeView。
3. `core/` 与 `session/` 的依赖闭包里**不许出现** `vue`、`@tiptap/vue-2`、`.vue`。
4. 面板 UI 只在 `components/lark-doc/` 写一份；Vue 3 / React 通过 element 复用。
5. 适配层只做三件事：props→options、事件转发、方法代理；**超过 150 行视为业务泄漏**。
6. 样式只走类名 + CSS 变量（`--lark-doc-*`），不依赖宿主的 scoped 机制。
7. 宿主可见契约（属性 / 事件 / 方法）改动必须同步 `web-component/attributes.js` + `docs/guide/web-component.md`。
8. `collab/` 之外不许 import `yjs` / `@hocuspocus/*` / `@tiptap/y-tiptap`。
9. **新增一种嵌入内容 = 加一条 `EmbedDef`**，不许新增块类型、不许 fork core。`core/embed/` 只做「URL → 节点属性」和「帧编解码」，**不发任何网络请求**；src 放不放行由 `policy/network` 决定。
10. **卡片/嵌入的动作一律冒泡**：按钮、提交、打开第三方页面都走 `emit('cardAction')` / `emit('embedOpen')`，编辑器不持 token、不直连第三方 API —— 否则一个文档编辑器就会变成"隐形的第三方 SDK 宿主"。
11. **正文永远是 DOM**：禁止把正文、表格块、代码块改成 Canvas/SVG 渲染；禁止自研渲染引擎、自研 OT、自研编辑器内核（飞书自己正文也是 DOM，理由见 §2.4.2）。**唯一允许 Canvas 的地方是画板/白板 —— 且只能通过 `webEmbed` 交给外部页面，本仓库不画。**
12. **画板类与超大型表格只准用成熟库**（Konva / Fabric / Univer / AG-Grid），且必须落在 iframe 或独立包内，不许进主包。
13. **不许新增"每次 view update 全量重扫文档"的代码**：新增派生视图（编号/大纲/折叠/搜索高亮）必须走 §3.7 的 `DerivedIndex`，禁止再写一个 `state.doc.descendants(...)` 挂在 `props.decorations` 里。CI 用 `check:architecture` 拦 `props.decorations` 里出现 `doc.descendants`。

### 2.4 性能分层（决策 6：学什么、不学什么、量级定在哪）

#### 2.4.1 四层责任 —— 性能从来不是单点优化

调研报告的结论是"飞书靠分层解耦，不靠 Canvas"。照抄这个框架，我们的四层落点如下：

| 层 | 责任 | 飞书怎么做 | 我们现状 | 本方案处置 |
| --- | --- | --- | --- | --- |
| **数据模型** | 增量的最小单位是块，不是整篇 | Block 树，40k 块上限 | ProseMirror doc **天然就是块树** | ✅ 已完成，只需保证"派生视图从 doc 算，不另建模型" |
| **协同** | 本地先改不等往返；通道分离 | OT + 乐观更新 + IndexedDB 缓冲 + awareness 独立通道 | 无（0.11.5 是单机） | → P6a：Yjs + awareness 独立通道（**不与正文同通道**，§5.7） |
| **渲染** | 只重绘变化的部分 | 脏矩形合并 + 离屏 + rAF 批量（Sheet/Bitable） | **装饰层每次 view update 全量重建**（6 次全文档扫描） | → **P7-01 脏区更新**，这是本期最大的单点收益 |
| **持久化** | 按访问模式分表，别一个大 blob | 元数据/OpLog/快照/会话/检索五套存储 | ** localStorage 一个 key 存整篇 + 一个 key 存 20 份整篇快照** | → **P7-02 IndexedDB 分层**（同时也是补需求 8 的欠账） |

> 报告 §2.4 的口径要抄下来提醒自己：飞书单文档 **40,000 块**，需求 13.17/1042/1148 给我们的基线是 **2,000 块 / 2MB**，差 **20 倍**。**本方案全部性能目标按 2,000 块定，不为 40k 做任何设计**。有人拿"飞书能开 4 万块"来要求优化，先回这一行。

#### 2.4.2 「学 / 不学」清单（进 §2.2 硬规则 11–13）

| | 项 | 判断 | 落点 |
| --- | --- | --- | --- |
| ✅ **直接对齐** | 块树、装饰不写正文、命令注册表、重依赖懒加载、输入不等持久化、按 transaction 增量渲染 | 已在做，**继续保持** | 现有能力，P0–P6 不许破坏 |
| ✅ **本期要做** | 脏区更新（装饰层）、IndexedDB 分层、派生数据快照（FVG 思想）、rAF 合并高频装饰、减少 DOM 层级 | 成本低、收益可测、**不改变任何语义** | **P7-01 ~ P7-04** |
| 🟡 **条件性** | 视口虚拟化 / `content-visibility` | **只有实测超标才做**，判据见 §5.9.2 | P7-05（可能不做） |
| ❌ **明确不做** | 正文 Canvas 化、自研渲染引擎、自研 OT、自研编辑器内核、复刻飞书 bug | 会丢浏览器原生能力（Ctrl+F / 选区 / 打印 / 读屏），且验证成本极高 | 写进硬规则 11 |
| ⛔ **只准用成熟库** | 画板/白板 → Konva / Fabric；大型表格 → Univer / AG-Grid | 自研 Canvas 引擎是"写了也证明不了它对"的典型 | 写进硬规则 12；画板在本方案里是 `webEmbed` iframe（§3.4），**连 Konva 都不需要** |

**为什么"减少 DOM 层级"值得单列**：飞书开源的 RTV（RichTextVista）在鸿蒙上做到万级列表 120 FPS，核心手段是"用属性字符串替代 Component 树"——本质就是**砍视图层级**。Web 上的等价物是：装饰用 `Decoration.widget` 的**一次创建复用**（已有 `key`）、能用 CSS 伪元素就不加真实节点。我们已经在做（折叠箭头/编号/列表 marker 都是 widget + key），P7 只需**审计有没有新增层级**。

#### 2.4.4 ESM 体积预算 110 KB → 118 KB（0.12 主题系统，实测后上调）

| 构建形态 | raw (B) | gzip (B) | 报告值 |
| --- | --- | --- | --- |
| 含 `feishu` + `pcvue` 两份 preset（现状） | 441,852 | 113,023 | **113.11 kB** |
| 摘掉两份 preset 后重构建 | 432,383 | 111,355 | 111.36 kB |
| preset 的边际成本 | — | **+1,668** | +1.67 kB |
| 旧预算 | — | 110,000 | 110 kB |

结论（三条）：

1. **preset 不是超限主因**：两份 preset 合计只值 1.67 kB gzip。
2. **110 kB 已不可达**：即使把两份 preset 全部摘掉（111.36 kB）**仍超旧预算 1.36 kB** —— 是 token 收编本身（L1/L2 两层 + `theme-dark.css` 内联进 ESM）把基价推过了 110 kB。
3. **非真性膨胀**：`grep -c katex dist/lark-doc.esm.js` = 0，KaTeX 未混入 ESM；CSS 内联是 ESM 构建既有形态（§3.6）。

处置：`size-limit[0].limit` `110 KB` → **`118 KB`**（现值 113.11 kB，留约 4.9 kB 余量）。

> 若要**守住 110 kB**，唯一路径是把 CSS 从 ESM 内联里摘出去（preset 拆成独立 CSS 文件、由宿主按需 import）并压缩 token 层 —— 这会改变 0.12 的分发形态，属决策项，**本次未做**，留给你拍板。

### 3.4 EmbedDef 与桥协议（决策 4 的核心，P3 前必须先定）

**先接受一个事实**：以后进来的东西形态只有两种 —— **能自己跑的网页**（本地绘图、Luckysheet、Figma、CodePen）和 **我们渲染的卡片**（任务调研、网页书签、问卷摘要）。所以只做两个节点，不做 N 个块。

```js
// core/embed/types.js —— 一个 def 描述"一种嵌入内容"，不是"一个块"
export const drawingEmbed = {
  id: 'drawing',                       // 稳定 id，写进 attrs.providerId
  kind: 'iframe',                      // iframe | card —— 决定用哪个节点渲染
  label: '画板', icon: 'pen', iconColor: 'b-500',
  tier: 'skeleton',                    // 复用 §3.2 的三档
  match: [/^https:\/\/draw\.example\.com\/d\/([\w-]+)/],   // 有序匹配，命中即用
  toAttrs: (url, m) => ({ src: url, resourceId: m[1], title: '画板', height: 520 }),
  sandbox: 'allow-scripts allow-forms allow-popups allow-downloads',
  allow: 'clipboard-write; fullscreen',
  bridge: { version: 1, required: ['ready', 'resize', 'setTitle', 'error', 'save'] },
  fallback: { poster: true, minHeight: 240 },
}
```

**为什么不是一个节点带 `kind` 属性**：`cardEmbed` 要参与文本流（可被搜索、可导出 PDF、可协同、可被评论锚定），`webEmbed` 是原子块（不可编辑、内容不进 CRDT）。两者 schema、序列化、导出行为都不同，混成一个节点会让每个下游都写 `if (kind === ...)`。

#### 3.4.1 `webEmbed` 节点（原子块）

| 属性 | 说明 |
| --- | --- |
| `providerId` | 命中的 `EmbedDef.id`；未命中为 `'generic'` |
| `src` | 规范化后的 URL（`embed` 地址优先，其次原 URL） |
| `title` / `height` / `aspect` | 标题栏文案、像素高、可选比例（两者取一，`height` 优先） |
| `poster` | 快照图（data URL 或远程，`offline` 时用它兜底） |
| `bridgeVersion` | 渲染时的桥版本，用于兼容老 iframe |

**正文/数据不进 JSON**：iframe 里的内容属于那个 app，我们只存"打开它的钥匙"（`src` + `resourceId`）。这条决定了嵌入块对协同、导出、体积都是零负担。

#### 3.4.2 桥协议 `lark-embed/1`

```js
// core/embed/bridge.js
// 帧：{ ns: 'lark-embed', v: 1, type, reqId?, payload }
// iframe → host : init-ack / ready / resize / setTitle / save / error / fullscreen
// host → iframe : init / theme / command / saveResult / destroy
```

| 规则 | 内容 | 为什么 |
| --- | --- | --- |
| 5 条必备能力 | `ready`（握手）/ `resize`（高度自适应）/ `setTitle`（标题栏同步）/ `error`（可读报错）/ `save`（应答即可，可为 no-op） | 少任何一条，要么高度塌陷、要么标题永不同步；`save` 必须有应答，否则宿主 3s 超时后把块标记为"未保存" |
| origin 校验 | host 只向 `new URL(src).origin` 发消息；收消息时 `event.origin` **必须等于**该 origin，且**不许**用 `event.source` 反推信任 | 不校验 origin 的 `postMessage` 等于给任意 iframe 开了编辑器后门 |
| 超时降级 | `init` 发出后 3s 收不到 `ready` → 走降级卡（poster + "在新窗口打开"） | 老站点不实现桥也必须能用，这是"骨架 23 项"能覆盖的长尾 |
| 版本协商 | host 发 `init { bridgeVersion: 1, capabilities: [...] }`；iframe 回 `ready { bridgeVersion }`。双方取**低版本** | 以后出 `/2` 时老 iframe 不炸 |
| 尺寸 | `resize` 只在变化 > 4px 时上抛，且 60ms 节流 | Luckysheet 这类每次重算都会狂发 resize，不节流会卡编辑器 |

**安全基线（写死，不许 per-app 放开）**：`sandbox` 不给 `allow-same-origin` + `allow-scripts` 的同源组合；`referrerpolicy="no-referrer"`；`allow` 仅按需给 `clipboard-write` / `fullscreen`；`src` 必须 https（`localhost` 仅 dev 例外）。

#### 3.4.3 URL 解析与 15 条预设

`resolveEmbed(url)` → 依次试 `match` 正则 → 命中返回 `{ def, attrs }`；全不命中 → 落 `cardEmbed` 的书签卡（不是"插入失败"，这点比飞书的"不支持"体验好）。

15 条预设写成**一个数据文件** `core/embed/presets.js`（每条 3–5 行），不是 15 个模块 —— 每条只做三件事：正则、规范化 URL、默认尺寸。这也是 P3 从 7–9 天变成 10–12 天却**风险反而下降**的原因：内核写一次，长尾靠数据。

### 3.7 DerivedIndex 契约（决策 6 的技术核心，P0 定签名、P7 填实现）

**先看现状有多贵。** `extensions.js:761` 的 `props.decorations(state)` 是 ProseMirror **每次 view update 都会调用**的钩子（不只是 docChanged，移动光标也会）。它内部依次做：

| 顺序 | 调用 | 复杂度 | 备注 |
| --- | --- | --- | --- |
| 1 | `foldableIdPositions(doc)` | O(N) | 建 blockId → pos 索引 |
| 2 | `findTextMatches(doc, query)` | O(N) | 搜索态才有内容，但**每帧仍跑** |
| 3 | `doc.descendants(...)` + 每块 `isFoldableBlock` + `foldedRange` | **O(N·k)，最坏 O(N²)** | `foldedRange → resolveHeadingSectionMode` 向前扫兄弟 |
| 4 | `computeHeadingNumbers(doc)` | O(N) | 全量重算编号 |
| 5 | `computeOrderedListNumbers(doc)` | O(N) + 每列表 `orderedListDepth`/`previousSiblingOrderedList` | |
| 6 | `computeBulletItems(doc)` | O(N) + 每列表 `doc.resolve` + 深度回溯 | |
| 7 | `DecorationSet.create(state.doc, all)` | O(N) | **丢弃旧集，不做 mapping** → ProseMirror 无法增量复用 |

**结论**：2,000 块文档里若有 200 个可折叠块，敲一个字要跑 ~200 次"向前扫章节" + 5 遍全文。这不是"可能慢"，是**结构性必慢**。而它恰好是"装饰不写正文"这个正确决定的**代价**——我们不能退回去把编号写进正文，只能让派生计算变便宜。

#### 3.7.1 契约形状

```js
// core/derive/index.js —— 派生索引：一次全扫 → 一棵树 → 事务后局部更新
export function createDerivedIndex({ doc, schema })   // 首次全量构建
// 返回值（P0 只定签名，P7 填实现）
{
  update(tr) -> { changed: Range[], index: DerivedIndex },  // 用 tr.mapping 算受影响区间
  decorations(state) -> DecorationSet,                      // 直接可用，不再重算
  headingNumbers(pos) -> { label, level } | null,
  outline() -> Array<{ pos, level, text, blockId }>,        // 大纲/目录复用同一份
  foldRanges(blockId) -> { from, to } | null,
  invalidate() -> void,                                     // 兜底：结构大变时整体重建
}
```

**四条实现纪律**（写进 P7 验收）：

1. **受影响区间来自 `tr.mapping`，不是 `tr.docChanged`。** 一个 transaction 可以有多个不连续改动（协同远端事务尤其如此，Yjs 一次 update 常含多处），所以必须遍历 `tr.mapping.maps` 收集 range 并合并；只取"第一个 changedRange"在协同下必然漏更新。
2. **只重扫"受影响区间 + 向外扩一级父块"**，不是全文。扩父块是因为块的属性（缩进、编号、折叠资格）依赖兄弟，父亲变了可能影响邻块。
3. **编号是唯一需要"向后传播"的派生量**：插入/删除一个 H2，会影响其后直到下一个 H1 的全部 H2 编号。所以索引里要存**每个标题的"下一个更高级标题位置"**，传播范围以它为界；原地改文字（不增删块）不传播。
4. **装饰集用 `oldSet.map(tr.mapping, tr.doc)` 打底，再对受影响区间做替换** —— 而不是 `DecorationSet.create(doc, all)`。这一条单独就能砍掉绝大部分 widget DOM 重建（现有 `key` 已在，不会有视觉抖动，但会省掉 diff 与挂载）。

#### 3.7.2 与协同的交叉约束（P6a 必须遵守，否则 P7 返工）

| 约束 | 原因 |
| --- | --- |
| `DerivedIndex` 对 **remote 事务与本地事务一视同仁**，都走 `tr.mapping` | 不能因为"远端来的"就整体 rebuild，那会把协同下的输入延迟放大到不可用 |
| 索引里**不存 `Y.Doc` / 不存 awareness** | 派生索引是 doc 的纯函数，协同状态属于 §5.7.2-5 的 UI 状态，两者不许混 |
| `gc: false` 的 Y.Doc 内存只增不减 | P6a 出口要单独检查"2,000 块 + 10 次重连后堆内存"，与 §2.4.3 的 120 MB 预算对齐；超了就必须上快照压缩 |

| 位置 | **独立仓库 / 独立 package `@lark-doc/collab-server`**，与本仓库无目录关系、无 workspace 关系、不进本仓 `files` |

| 为什么必须分开 | ① Node 版本不同（本仓构建链 Node 14，服务端 18+）；② 发布节奏不同（客户端跟版本走，服务端跟部署走）；③ 服务端要接 Postgres/Redis/鉴权/多实例，属运维领域，塞进来会把 `files` 白名单和 CI 一起搞脏 |
| 契约版本 | `COLLAB_PROTOCOL_VERSION = 1`（已在 §3.3 导出），握手时双向校验；不一致 → 客户端报 `E_PROTOCOL_MISMATCH`，**不回退、不静默、不半连** |
| 文档键 | `documentId` 由宿主给（建议 `<workspaceId>/<docId>`），服务端只当不透明字符串，不做解析 |
| 落盘格式 | 服务端负责；契约写死"键 = documentId，值 = `Y.encodeStateAsUpdate` 二进制"，**与 Yjs 小版本解耦** |
| 鉴权 | `onAuthenticate({ token, documentName })` → `{ user: { id, name, color }, capabilities }`；失败直接拒连。`capabilities.canEdit=false` 时**服务端也要拒写**（客户端 `setEditable(false)` 只是 UI，双保险才算数） |
| 版本快照 | 契约里定 HTTP 形状：`POST /documents/:id/snapshots`、`GET /documents/:id/snapshots/:sid`，返回二进制 + 元信息；编辑器只消费，不实现 |
| 开发联调 | e2e 内 `import { Server } from '@hocuspocus/server'`（`devDependencies`）起**内存实例**、随机端口、`extensions: []`。这是本仓库唯一出现的"服务端"，且是**第三方库调用，不是自有代码** |
| 代理 | nginx `proxy_set_header Upgrade/Connection` + `proxy_read_timeout 3600s` —— 写进本仓文档，代码留在对面仓库 |

> **这条边界怎么守**：CI 里加一条断言 —— `git grep -l "hocuspocus/server"` 的结果只能是 `test/` 下的文件。出现第二个位置就红。这条比"靠自觉"可靠，因为"临时加个开发服务器"永远是从一个 script 开始的。

#### 5.7.4 协同验收（e2e，双上下文）

| 用例 | 断言 |
| --- | --- |
| C1 双向同步 | A 输入 → B 500ms 内出现同一文本 |
| C2 并发同位置插入 | A、B 同时在同一段插入不同字符 → 两端最终 `getText()` 完全一致 |
| C3 撤销隔离 | A 撤销 → 只撤 A 自己的输入，B 的不变 |
| C4 断线重连 | B 断网 5s 期间 A 继续编辑 → B 重连后补齐，无重复无丢失 |
| C5 块 ID 稳定 | 并发编辑后两侧 `blockId` 集合一致，且不出现"同一块两个 ID" |
| C6 只读端 | C 以 `canEdit:false` 加入 → 能看实时更新，本地不可输入 |
| C7 首次播种 | 同一文档 3 个客户端依次进入 → 初始正文只出现一次 |
| C8 折叠不串台 | A 折叠某标题 → B 的视图不受影响 |
| C9 嵌入块协同边界 | A、B 同时打开同一含 `webEmbed` 的文档 → 两端 iframe 各自独立加载（不互相驱动）；改标题/高度 → 两端 attrs 同步；`src` 冲突以最后写入为准 |

> **C9 定的是一个边界，不是缺陷**：iframe 里的运行时归那个 app 管，我们只同步"打开它的钥匙"。若那个 app 自己也支持多人协同（Luckysheet 可以），多人同时编辑由它负责；我们**不假装**替它做协同。这条写进文档，避免以后被当 bug 提。

**P6a 出口**：C1–C9 全绿（服务端用第三方 `@hocuspocus/server` 内存实例）；断网重连 10 次无内存泄漏（`Y.Doc.destroy()` 后 listener 归零）；主包体积不变（协同全在 `collab` 子入口）；**本仓库不含任何自有服务端代码**（CI 断言 `hocuspocus/server` 只出现在 `test/`）。

#### 5.7.5 四项此前悬空的设计决策（**已定，B22–B25 收口**）

> 这四项原列在 [10 §2](./10-缺口与待补清单.md) 的 B 级「未采」，性质是**定义缺口**（采集解决不了）。下面是拍板结论，实施时照此写，不再讨论。

**① 折叠 / 大纲展开 / 侧栏宽度存哪儿（B22）→ 本地 storage，单文档一个 key，不进 Y.Doc、不进 awareness。**

| 项 | 决定 |
| --- | --- |
| 存储位置 | `localStorage`，key = `tiptap-vue2:lark-doc:ui-state:<documentId>` |
| 存什么 | `{ collapsed: string[], outlineOpen: boolean, sidebarWidth: number, updatedAt: number }` |
| `collapsed` | **只存折叠着的 `blockId` 数组**（默认全展开 → 空数组；不存"展开"的，避免文档变长后 key 膨胀） |
| 容量闸门 | 上限 **500 条**；超限按 `updatedAt` 淘汰最旧（折叠是廉价 UI 态，丢失无损失） |
| 为什么不走 awareness | awareness 是**易失的在场通道**（断线即清、刷新即丢），塞 UI 态会得到"刷新后折叠全没了"；而且协同方**不该看到**别人折叠了什么（vs C8 用例） |
| 为什么不进 Y.Doc | 进了就是"别人折叠我的标题"（§5.7.2-5 已定性为 bug），且会污染撤销栈 |
| 降级 | localStorage 不可用（隐私模式）→ 内存 Map，本次会话有效；不报错、不提示 |
| 读写时机 | 折叠切换后 **300ms 防抖**写；打开文档时读一次，读失败按空处理 |

**② 离线应急快照的写入频率与上限（B23）→ 节流 30s、单份覆盖、512KB 硬顶。**

| 项 | 决定 |
| --- | --- |
| 触发 | `collaboration.connect()` 返回 `disconnected` 时启动；`synced` 时**立即清空并停表** |
| 首次 | 进入 disconnected **立刻写一次**（不等 30s，否则刚断网就关页面等于没写） |
| 之后 | 每 **30s** 检查一次，**且仅当 `docChanged` 为真**才落盘（无改动不写，避免空转） |
| 份数 | **只保留 1 份**（同一个 key 覆盖写，**不是数组**）。历史 20 份整篇快照的做法（P7-02 要修的配额问题）不许在这里重演 |
| key | `tiptap-vue2:lark-doc:offline:<documentId>` |
| 体积闸门 | 序列化后 **> 512 KB → 放弃本次写入**，置 `offlineDraftSkipped = true`（UI 只在"已断开"提示条上加一行「本次离线改动过大，未保存草稿」）。**不截断、不分片** —— 截断的草稿比没有草稿更危险 |
| 恢复 | `synced` 后若本地存在快照 → **不自动合并**，只 console 提示并提供「下载离线副本」入口（CRDT 已经收敛，合并会产生重复内容） |
| 内存 | 不缓存整个 JSON 字符串（每次现序列化），避免大文档常驻两份 |

**③ 8 项 capability → UI 置灰映射（B24）→ 见 [05 §5.3.1](./05-接口文档.md) 的完整映射表；`onAuthenticate` 返回的就是同一套 8 项。**

| 约束 | 决定 |
| --- | --- |
| 唯一真源 | **只有一套**：05 §5.3 的 `Capabilities` 8 字段。服务端 `onAuthenticate` 返回的 `capabilities` 是**同一结构的子集**，经 `normalizeCapabilities` 浅合并（缺省即 true）后落到 `session.can()` |
| 校验时机 | ① 握手时（`onAuthenticate`）；② 打开文档时（`getCapabilities`）；**两处结果冲突取交集（更严的一侧）**，防止"握手给了编辑权、进文档却只读" |
| 落点 | UI 只读 `session.can(key)`，**不许**各自 `if (role === 'owner')` 另判一套 |

**④ `poster` 快照谁生成 / 何时 / 多大（B25）→ `EmbedDef` 静态配置，随包发，不做运行时截图。**

| 项 | 决定 |
| --- | --- |
| 生成者 | **`EmbedDef` 里的静态字段** `poster`（一条 embed 一份，写在 `core/embed/*.js`），**不截图、不调服务** |
| 为什么不能运行时截 | iframe 跨域 `toDataURL` 必失败；headless 截图要服务端浏览器（违反"服务端不在本仓"）；首屏同步渲染也等不起 |
| 数量与体积 | 15 条 `EmbedDef` → **15 张 webp，16:9（960×540），单张 ≤ 40 KB**，合计 ≤ 600 KB，**走懒加载**（`poster` 只在 `offline` 或加载失败时才插入 DOM，正常态不下载） |
| 字段 | `poster: string` —— 支持 `data:` URL 与远程 URL；缺省取 `def.poster`；宿主可通过 `attrs.poster` 覆盖（存的是 URL，**不存 base64**，避免正文 JSON 膨胀；实测飞书正文里也不存 base64） |
| 何时用 | ① `offline` 模式；② iframe `onerror` / 3s 超时降级；③ 导出 PDF（避免嵌入内容空白）。三种场景**同一张图**，不另生成 |
| 占位兜底 | 连 `poster` 都没有（未知 `providerId`）→ 用 A17 的**降级卡通用 chrome**，不画空框 |

#### 5.9.2 虚拟化的判据（写死，避免"顺手做了"）

**先记住为什么默认不做**：窗口化虚拟化会让 ProseMirror 的 doc 与 DOM 不再一一对应，于是**浏览器原生 Ctrl+F 找不到未渲染内容、打印缺页、跨块选区断裂、读屏跳读** —— 这四样恰好是调研报告里"正文必须用 DOM"的**同一条理由**。为了性能砍掉它们，是把一个好补的问题换成四个难补的问题。

| 触发条件（任一） | 动作 |
| --- | --- |
| 2,000 块文档首屏可输入 > **1.5 s**，且 P7-01/02/03 做完仍不达标 | 先加 `content-visibility: auto`（1 天，可回退），**仍不达标才考虑窗口化** |
| 滚动 < **40 FPS**，且 P7-01 做完仍不达标 | 同上 |
| 上述都不触发 | **不做**。把这条写进 `docs/guide/performance.md`，以后有人提"为什么不做虚拟化"直接指这里 |

> 需求 1042 写的是"加载采用分页/虚拟化"——它要的是**结果**（长文档不卡），不是手段。`content-visibility` 与"分页加载"都能满足结果，且都不破坏原生能力。这是本方案对需求原文的一处**有理由的偏离**，已在此标注。

## 7. 交付方式（决策 2：只发 GitHub）

**每期收口一条命令**：

```bash
# 只推 GitHub：bump 到 beta.N、跑全链 check、commit、打 tag、push，不发 npm
npm run ship -- --version 0.12.0-beta.2 --skip-publish --include-new -m "feat(p1): 块容器语义与 schema v2"
```

- `--skip-publish`：跳过 registry 占用检查与 `npm publish`（已验证该参数存在，`release.sh:69`）。
- `--include-new`：**必须带**。默认是 `git add -u`，新文件不入库（P0–P6 每期都有大量新文件）。`scripts/verify-vditor-real-data.js` 已进 `.gitignore`，所以带这个参数不会误带本机脚本。
- 版本号写 `0.12.0-beta.N`，tag 也按此命名；npm 上**不存在**这些版本，即不会有人误装。
- 正式版：`next/0.12 → master` 合并后 `npm run ship -- --minor`（0.11.5 → 0.12.0，正常发 latest）。

**每期 tag 一览**：`beta.1`(P0) `beta.2`(P1) `beta.3`(P2) `beta.4`(P3) `beta.5`(P4) `beta.6`(P5) `beta.7`(P6a) `beta.8`(P6b) `v0.12.0`(P7)。**共 9 个可回溯点**。P6b 之后、P7 之前不再有 `v0.12.0` —— 性能期没跑完就不算 0.12 完成，这是刻意的。

**为什么不用 `--git-only`**：它不动版本号、不打 tag（`release.sh:186`），拿不到"每期一个可回溯点"。所以走 `--skip-publish --version ...`。

**协同服务端（决策 5）不在本仓发布节奏里**：`@lark-doc/collab-server` 独立仓库独立发版，版本号只受 `COLLAB_PROTOCOL_VERSION` 约束（协议 1 可以对应服务端 1.x 的任何小版本）。本仓 `package.json` 不引用它，`devDependencies` 里只有第三方的 `@hocuspocus/server`。

## 8. 分支与合并（沿用 08，只补决策 2 的简化）

| 项 | 规则 |
| --- | --- |
| 长驻分支 | `next/0.12`（功能） / `master`（只修 bug） |
| 每期 | `feat/pN-xxx` → `--no-ff` 回 `next/0.12` |
| 回流 | 每 3 天 `next` 上 `git merge master`（单向）；单条 hotfix 用 `cherry-pick -x` |
| 发布 | next 上只 `--skip-publish`；master 上才真正 publish |
| 合 master | 整期稳定 + 三端 e2e + 协同 e2e 全绿 → 一次 `--no-ff` + `npm run ship -- --minor` |

**唯一新增的脚本改动（P0-08）**：`release.sh` 预检处加一条硬拦截——非 `master` 分支且未带 `--skip-publish` → `die`。现状只是 `warn`（`release.sh:162`），在"next 上永远不该发 npm"的新规则下必须变硬。

**六项决策已全部落定**，v2 遗留的两个待确认项与一个开放项均已关闭：

| 原问题 | 结论 | 方案落点 |
| --- | --- | --- |
| `iframe` 骨架是否接受"不接真实服务" | 接受，且要求能承载以后的本地绘图 / Luckysheet / 任务调研 | 升级为**内核方案**（§3.4 / §3.5 / §5.4）：2 节点 + 注册表 + 版本化桥；15 条预设退化为配置 |
| 协同服务端进不进仓库 | **不进**，独立 package | §5.7.3：本仓只留客户端 + 契约文档 + e2e 用第三方内存实例；CI 断言守边界 |
| 性能要不要进这一轮 | **进，但排在最后且按实测驱动** | §2.4 分层 + §3.7 派生索引 + §5.9 P7；虚拟化列为条件性，默认不做 |

**最后一个开放项，我直接给默认决定（可随时推翻）**：P3-07 的本地绘图参考实现，**先自写一个 ≈200 行的最小画板页**，放在 demo 里专测桥协议。

- 理由：先接真实应用，协议会被那**一个**应用的脏细节带着走（它的总线、滚动容器、快捷键拦截方式都会变成"事实标准"）；先自写验证，能把 `ready / resize / setTitle / save` 的语义压干净，之后接真的才不会反复改协议。
- 代价：那 200 行不能当产品用 —— 它本来就只是**协议测试夹具**。
- 推翻成本：极低。等你那边的绘图应用就绪，加一条 `EmbedDef` 就能上，这 200 行留在 demo 里继续当回归用例。
