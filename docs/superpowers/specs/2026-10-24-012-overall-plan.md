## 0. 为什么需要这份文档

superpowers 的 `writing-plans` 有一条 Scope Check：

> If the spec covers multiple independent subsystems, it should have been broken into sub-project specs during brainstorming. Each plan should produce working, testable software on its own.

`09` 是一个覆盖 **8 期、9 个交付点**的大 spec，显然不是"一个 plan"。所以先在这里拆开、排序，再逐个进 `writing-plans`。

**一个纠正**：此前我把范围收敛成了"主题切换"单个项目。不对——主题切换是 0.12 里的**一个子系统**（§4 中的 T），不是全部。

## 1. 目标 / 非目标 / 反目标

### Goals

| # | 目标 |
|---|---|
| G1 | **页面与飞书预期一致，交互与飞书一致**（1:1 复刻）——这是总验收口径，高于任何单项指标 |

| # | 失败形态 |

| A1 | 与飞书**视觉或交互不一致**——但满足了任务单的勾选项 |

## 5. 我的流程（superpowers 落地图）

```text
① brainstorming  ── 已完成（09 六项决策 + 主题设计文档已批准 + builder check 已过）
        │
② 本文件：Scope Check 拆分与排序  ── 当前位置
        │
③ 逐个 writing-plans
        │    每个子系统 → docs/superpowers/plans/2026-10-24-<name>.md
        │    含：文件级 create/modify 清单 + Interface 契约 + 逐步「写失败测试→跑→实现→跑→commit」
        │
④ 你选执行方式（每个 plan 出后各选一次）
        │    subagent-driven（每任务一 subagent + 每任务 review）
        │    native（我自己跑，最后一遍 review）
        │
⑤ executing-plans / subagent-driven-development（连续执行，中途不停）
        │
⑥ verification-before-completion（铁律：无当场验证输出，不声称通过）
        │
⑦ finishing-a-development-branch（测试绿 → 探测环境 → 给选项 → 执行 → 清理）
```

**每一步的硬规则**：

| 阶段 | 规则 |
|---|---|
| ③ | plan 里每个任务必须能独立跑绿；补规格与写代码**分开**，先规格后代码 |
| ④ | 未选执行方式不动手 |
| ⑤ | 连续执行，不在任务之间停下来问"要不要继续" |
| ⑥ | 没跑过的命令不许声称通过；10 套断言（74/38/16/7/23/30/14/12/91）是回归底线 |
| ⑦ | 发布走 `npm run ship`，不手工摸索（项目既有约定） |

## 6. 每期闸门（09 §6 门禁，此处只列触发点）

| 闸 | 条件 |
|---|---|
| check 链 | `npm run check` EXIT=0 且 **0 warning** |
| 断言 | 10 套全绿，不回退 |
| 性能 | `check:perf` 退化 > 20% 即失败（**P0-10 起每期跑**） |
| 体积 | `size-limit` 四个预算不涨 |
| 架构 | `check:architecture` 依赖方向正确（P0-09 起） |
| 发布 | 非 master 且未 `--skip-publish` → `release.sh` **die** |
