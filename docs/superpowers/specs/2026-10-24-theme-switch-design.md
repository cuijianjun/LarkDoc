## 1. Intent · 要什么，为什么

给 lark-doc 加主题切换，**1:1 对齐飞书**，并且要能在真实宿主（pcvue-1023）里正确跟随。

真正的动机不是"加个深色模式"，而是下面这个已经存在的问题：

> 宿主 pcvue-1023 **早就有一套多主题**（`html[data-skin]` + SCSS `$themes`），但 lark-doc 完全没接上——
> `LarkDoc/index.vue:68` 把 `theme` **写死为 `'light'`**，容器 `.lark-doc-wrapper` 背景**硬编码 `#fff`**。
> 于是宿主切深色后，编辑器是一整块白，四周还露一圈白边。**这个今天就能复现。**

飞书官方口径里最关键的一条（帮助中心 784578188399 / 849872303611，已核实）：

> **深色模式下，可单独勾选「用浅色模式查看文档、邮件内容」。**

也就是说 **UI 外壳与正文纸张是两个正交维度**。对一个嵌入式编辑器 SDK 来说这是刚需——宿主站点是深色、文档纸张要保持浅色，是常见场景。这直接决定了本设计的核心形态：**双轨**。

## 2. Goals / Non-goals / Anti-goals

### Goals（做到什么算成）

| # | 目标 |
|---|---|
| G1 | `light` / `dark` / `system` / `host` **四态**可用；`host` 能跟随宿主 `html[data-skin]` 实时变化 |
| G2 | **UI 外壳与正文纸张可独立设置**（双轨）：深色外壳 + 浅色纸张是合法组合 |
| G3 | 首屏**无闪烁**（FOUC）；系统主题变化时实时响应；多标签页同步 |
| G4 | 打印时正文**强制回浅色**（现有 `@media print` 只强制了 `background:white`，深色下会打出黑纸） |
| G5 | 新增硬编码色值**被 lint 拦住**——247 处存量可以慢慢还，但不允许再涨 |
| G6 | 在 pcvue-1023 里切深色，编辑器与宿主视觉统一、无白块白边 |

### Non-goals（本期明确不做）

| # | 不做 | 原因 |
|---|---|---|
| N1 | 飞书 5 种主题色（苍穹/天际/晴空/湖光/曜石） | 官方口径：**仅桌面端**。只暴露 `--ld-brand` 供宿主覆写 |
| N2 | 统一现有"绿蓝混用" | 是既存视觉偏差，不是主题引入的。单开任务 |
| N3 | 自定义主题编辑器 / 用户自定义色板 | 超出范围 |
| N4 | 0.12 主线 P0 的 core 抽取 | 另一条线，本设计不覆盖 |

### Anti-goals（技术上能跑通也算失败的情况）

| # | 失败形态 |
|---|---|
| A1 | 深色下**有区域漏色**（白底残留、深色文字不可读）——半套深色比没有更糟 |
| A2 | 双轨互相污染：改 `theme` 影响了正文，或改 `contentTheme` 影响了工具栏 |
| A3 | 首屏闪一下白再变深色 |
| A4 | 收编过程中**改变了浅色的视觉**——浅色必须逐批截图 diff 零变化 |
| A5 | token 只建在 Vue2 层，导致 React/Vue3 适配各裂一套 |

## 4. Approaches · 考虑过的做法与取舍

三条都是真实可行的，不是陪跑。

### A · 收编先行

先把 221 处 hex + 26 处 `white` 全量收编进 token（4 人日，按 CSS 行段分六批逐批截图 diff），再建双轨机制，最后上深色。

- **优点**：地基纯净，深色一上就全，没有半吊子中间态。
- **缺点**：**前 4 人日零可见产出**；且整个 T0 必须排在 P0-01 删文件之后（C5），否则给即将被删的文件收编色值是白做工。
- **代价**：最大不确定性（双轨能否真正切开）要等 4 天才验证得到。

### B · 机制先行 + lint 止血 ✅ **选定**

先建 token 层骨架 / 双轨机制 / lint 规则（约 2 人日），收编按「**跨界 > 高频 > 长尾**」三批穿插在后面。

- **优点**：
  1. **最早验证双轨**——这是本项目最大的不确定性，不是"247 处怎么替换"（那是体力活）；
  2. **lint 立刻止血**，是唯一能让债务停止增长的东西，越早接越省；
  3. 机制层不碰 `CodeNode.vue` / `ImageNode.vue`，**不受 C5 阻塞**，可以现在就动。
- **缺点**：中间态是半套深色（先覆盖跨界 + 高频，长尾后面还）。
- **缓解**：中间态只对内部可见，配合 lint 不会继续恶化；长尾收编排在采色之前完成。

### C · 宿主最小闭环

只做 `theme:'host'` + 主色对齐 + 容器背景变量化（3 人日），完整深色延后。

- **优点**：立刻解决 pcvue 现有白块问题，可见收益最快。
- **缺点**：不解决根本，硬编码继续涨，后面还是得回来做 A 或 B。

### 为什么选 B（一句话）

> 双轨能不能真正切开 UI 和正文，是这活儿唯一可能推倒重来的地方；B 两天就能验证它，A 要四天，而 lint 早一天接上就少一天债务。

## 5. 已决事项 · how 里被定下来的部分

### 5.1 双轨模型（核心）

```
theme        : 'light' | 'dark' | 'system' | 'host'   → UI 外壳（工具栏、菜单、浮层、滚动条）
contentTheme : 'light' | 'dark' | 'auto'              → 正文纸张（编辑区底色、文字）
```

- `contentTheme: 'auto'` 时跟随 `theme`，退化成普通单轨，零额外成本。
- 落 `data-theme` + `data-content-theme` 两个属性，CSS 按属性选择器命中。

### 5.2 四态与 `host`

宿主 **0 个 CSS 变量**（C4），所以 `var(--宿主变量)` 继承路线直接死掉。第四态 `theme:'host'` 的做法：

- `MutationObserver` 监听 `documentElement` 的 `data-skin` 属性变化；
- 经 **`hostSkin.map` 映射表**（宿主 skin 名 → lark-doc 主题名）转换；
- 未命中则 fallback 到 `light`。
- 规格见 11 §3.9（R1–R6）。

### 5.3 token 建在哪

**必须建在 core**（C6）。建在 Vue2 层会导致 React / Vue3 适配各裂一套色板。

跨界 token（既用于外壳又用于正文的）**必须拆成两套**：

```
--ld-<name>-chrome     /* UI 外壳 */
--ld-<name>-content    /* 正文纸张 */
```

不拆，双轨会互相污染（A2）。

### 5.4 不用 CSS `light-dark()`

`light-dark()` 只认单维 `color-scheme`，**表达不了双轨**。手写属性选择器。

### 5.5 两套深色档，不二选一

| 档 | 底色 | 适用 |
|---|---|---|
| 默认（中性灰） | `#17181A`【推导·待实测】 | 通用宿主 |
| `theme-preset-pcvue.css`（墨绿） | `#1d3d39` | pcvue-1023 |

原因：宿主深色是**墨绿系不是中性灰**（底 `#1d3d39`、菜单/边框 `#425756`、表格线 `#4b5b5c`、阴影 `none`）。只给一套，要么祸及其他宿主，要么在 pcvue 里突兀。

### 5.6 打印

现有 `@media print` 强制 `background: white`，但深色下**必须强制正文回浅色**，否则打出黑纸。

### 5.7 收编三批序

1. **跨界**（拆 `-chrome` / `-content`）—— 决定双轨能否成立，最优先
2. **高频**（出现次数 Top 的唯一色值）
3. **长尾**

浅色必须**逐批截图 diff 零变化**（A4）。

### 5.8 与主线 P0 的交叉（来自 10 §6.1）

| # | 交叉 | 处置 |
|---|---|---|
| X1 | P0-01 删 CodeNode/ImageNode vs 收编 | B 的机制层**不受阻塞**；收编跳过这两个文件 |
| X2 | P0-07/08 建 CI vs lint 接入 check 链 | lint **先写**，接入放 CI 之后 |
| X3 | P0-10 性能基线 vs mermaid 重渲染 | 有基线才敢验证重渲染没退化 |
| X4 | P0-03 拆 SFC vs 收编 CSS | ✅ 不冲突（CSS 是独立全局样式） |
| X5 | core 零框架 + 三端适配 vs token 归属 | ⚠️ token **必须建在 core** |

### 5.9 收编边界 · 长尾不强制（我的决定）

实测 121 个唯一色中 **79 个只出现 1 次**。若强制全量 token 化：

- 要么近似合并 → 违反 A4「浅色零变化」，验收标准作废；
- 要么 token 膨胀到 100+ → T0 翻倍。

**决定**：只收编**跨界 + 高频**两类；**长尾（单次出现的 79 个）保留字面值不动**。
lint **只卡新增**，不强制存量清零。深色覆盖长尾时，用作用域内的深色覆盖规则处理，不改浅色定义。

→ A4 守住，T0 不翻倍。

### 5.10 `contentTheme` 作用域判定规则（我的决定）

> **判定规则：浮层 / 固定定位元素一律归 `-chrome`（跟 `theme`）；纸张底色与正文文字归 `-content`（跟 `contentTheme`）。**

据此逐项定性：

| 元素 | 归属 | 理由 |
|---|---|---|
| block-handle、表格工具条、slash 菜单、气泡条、tooltip | **chrome** | `position: fixed/absolute` 的浮层 |
| AI 面板、侧边栏 | **chrome** | 纸张之外的 UI 外壳 |
| `.lark-doc-slide-stage`（`background: white`） | **content** | 内容舞台，属纸张侧 |

### 5.11 主色口径（澄清文档内部矛盾）

`11 §3.4` 表中 `--ld-brand` 的浅色值写的是飞书蓝 `#1456F0`，但 N2/R4 说本期不动主色——两条冲突。

**澄清**：`#1456F0` 是**1:1 目标值**，**本期不动**。T0 沿用现有绿系，浅色视觉零变化；切蓝单开任务（与 N2 同）。

### 5.12 token 落点 · 先建现有 CSS，P0 后迁（已拍板 2026-10-24）

`src/core` 目前只有 3 个 js、**无样式层**，"建在 core"今天没有物理目标。

**决定**：token 层先建在现有 `src/components/lark-doc/lark-doc.css`，等 P0 的 core 抽取落地后再迁移。

- **理由**：与"甲先乙后"一致——现在新建 core 样式等于提前做 P0 的一部分；且不改变发布形态（宿主无需多引一个 CSS）。
- **承接的代价**：A5（三端各裂一套）的风险向后顺延；P0 后需做一次迁移。因 token 定义集中在一个文件，迁移成本可控（移动文件 + 调整引入路径）。
- **迁移触发条件**：P0 建立 `core` 样式层之日。

### 5.13 持久化默认关（已拍板 2026-10-24）

11 §5.8 的 `themeStorage` 未给默认值。

**决定**：**默认不落盘**。

- **理由**：C7 优先——默认落盘会让现有宿主首屏突变深色，属破坏性变更。
- **连带修订**：G3 的「多标签同步」与「首屏防闪」两条，改为**仅在 `themeStorage` 显式开启时验收**。
- 宿主想要持久化，需显式传 `themeStorage: 'local'`。

## 8. 验收（对应 Goals）

| Goal | 怎么证明 |
|---|---|
| G1 四态 | 四态各自渲染一致；`host` 下改 `html[data-skin]` 实时跟随 |

| G3 无闪烁 | 首屏无白闪；系统切换实时响应；多标签同步；`prefers-reduced-motion` 下无动画 |
| G4 打印 | 深色下打印预览正文为浅色 |
| G5 lint | 新增一处硬编码 hex → lint 失败 |
| G6 宿主 | pcvue 切 dark，编辑器与宿主统一、无白块白边 |
