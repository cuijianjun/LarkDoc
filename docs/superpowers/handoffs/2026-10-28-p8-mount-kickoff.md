## 2. 与 P7-05 的关系：不推翻它

P7-05 的判据是「滚动稳态 ≥ 40 FPS 就不做窗口化」，实测 60.3 FPS，结论成立，且**P8 同样不走窗口化**。
两条理由原样有效：

- `content-visibility: auto` 治**绘制**，不治**建 DOM** —— 屏外节点照样创建、装饰照样计算；
- 窗口化打穿四条契约（折叠/高亮的整棵缩进子树、查找的全文档命中数、目录的跨屏定位、导出/保存的全文本）。

P8 换靶子也换手段：**不动滚动，改首屏的灌入节奏**。这是 P7-05 从未评估过的方向 ——
它当时只回答「要不要给滚动加窗口化」，没有回答「能不能不一次性同步灌满 2,000 块」。

## 3. 已知与未知

**已知：**

- `scripts/perf/measure.mjs:147` 直接 `editor.commands.setContent(contentHtml)`，**不走持久化 / 水合路径**
  → 这个数字是「同步建 2,000 块 DOM」的结构性成本，不是 P7-03 早期水合的靶子（P7-03 已明确不指望它）。
- fixture 是 `buildDocHtml({ seed: 42, blocks: 2000 })`：文本段落 / 标题+缩进子块 / 嵌套列表 / 表格 / 引用混合。
- 2,000 块 ≈ 1.5 MB JSON；装饰集实测 1424 条、可折叠块 478 个。

**未知（Phase 0 必须回答）：**

1. 36.7 s 的分项构成：HTML parse / schema 构建 / DOM 创建 / 首次 layout / 装饰计算 / focus 各占多少。
2. 单块成本是否随文档增大而超线性（若是，说明有 O(n²) 隐藏项）。
3. 2,000 块里最大的 10 块（表格、深层嵌套列表）占多少 —— 决定「先修大块」还是「先改节奏」是否划算。

**这个问题与 `decorationIncrementalMs` 的 78.8 ms 是同一类**：端到端数字有了，分项归因从未做过。
P7 已经因为「把推测当结论」返工过一次（`perf/report.md` 的订正块），P8 不允许重演。

## 4. 候选方案与取舍

| 方案 | 做法 | 预期收益 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A 分段渐进灌入** | 首屏只 `setContent` 前 N 块（N≈200），其余用 `requestIdleCallback` 分片 append；补齐完成前挂 `hydrationComplete = false` | 首屏可交互进 1.5 s 量级（取决于 N） | ① 后台插入与用户编辑的 pos 冲突要 mapping；② 查找/目录/保存/导出在未补齐时的语义必须定死；③ 需要一道与 P7-03 `outlinePending` 同构的闸门 | **首选，但需 Phase 0 支持** |
| B 窗口化（虚拟挂载） | 只渲染视口附近块 | 首屏 ↓、滚动仍需托管 | 打穿四条契约 | 不做（P7-05 已否，P8 维持） |
| C `content-visibility: auto` | CSS 跳过屏外绘制 | ≈ 0（不治建 DOM） | 滚动条跳变、目录定位二次校正 | 不做 |
| D 合并小段为大块 | 减少 DOM 节点数 | 近似线性下降 | 破坏块级语义、协作与选区连续性 | 不做 |
| **E 归因先行** | 给 `setContent` 全链打点，产出分项表 | 0（信息） | 一次探针开发 | **Phase 0，必做** |

## 5. 建议路线

**Phase 0（归因，独立任务）** → 决策点：DOM 创建 + parse 是否占 ≥ 60%？

- 是 → 走 A（分段灌入），因为成本确实在「一次性建 DOM」上；
- 否 → 先修归因出的最大分项（很可能是首次 layout 或装饰计算），A 顺延。

**Phase 1（A 落地）**，按契约拆分，顺序不可颠倒：

1. `hydrationComplete` 闸门 + 首屏 N 块灌入（复用 P7-03 `outlinePending` 的收口方式：置位、守卫、UI 禁用、实测覆盖后落下）。
2. 未补齐状态下的四条契约语义：
   - **保存 / 导出**：必须强制补齐后再取正文（否则写出去是半篇，这是硬红线）；
   - **查找**：补齐前只在已灌入区搜索，并在面板上明示「文档仍在载入」—— 不能给出「0 命中」这种错误答案；
   - **目录**：用 P7-03 的 `derived` 快照先挂完整目录，跳转到未灌入区时先补齐再跳；
   - **折叠 / 高亮**：装饰只对已灌入区生效，补齐后由既有 `invalidate()` 全量重算。
3. 编辑冲突：用户在已灌入区编辑时，后台插入必须走 `tr.mapping`，或暂停补齐直到 idle 稳定。
4. 全量门禁 + 文档回填。

## 6. 验收判据

- `mountToTypeableMs` **≤ 1500**（2,000 块 fixture，机器空闲时采，样本数 ≥ 20，取 p50）。
- 现有 **1674** 条用例零回退；`check:gate` / `check:artifacts` / `check:perf` 三门禁 EXIT=0。
- `keystrokeP95Ms` 不得因改造变差 > 20%（门禁现有口径，不要求达标）。
- 四条契约的**等价性用例**：查找全量命中数与改造前逐一相同、折叠范围一致、目录跳转落点一致、导出字节一致。

## 7. 风险与回滚

| 风险 | 处置 |
| --- | --- |
| 后台插入把用户正在编辑的位置顶掉 | 用户编辑期间暂停补齐；补齐前记 `tr.mapping` |

| 候选 | 做法 | 预期 | 风险 |

**建议顺序：先 B，再按需 A。** B 语义最保守（动的是一次事务的形状，不是 schema）、可纯单测；

**为什么 P8-03/04 降为条件任务**：它们服务的是「分段灌入」这条路线。P8-01b 证明成本不在
「一次性建 DOM」（599.9 ms），而在补 id 事务 —— 把步数压下去之后，首屏就不必再分期灌入，
四条契约的补齐语义、编辑冲突 mapping 随之失去必要性。若 B/A 实测拿不到量级收益，再回到 P8-03/04。

### P8-01 归因（已完成；**结论已被 P8-01b 订正，本节保留原始记录**）

> **订正声明**：下面表里的「解析（HTML 轮 − JSON 轮）= 38,376.8 ms / 97.3%」**是错的**。
> 那一减法的两轮之间差了**两个**变量（解析路径、`blockId` 有无），真正被减掉的是
> 一笔 **7,932 步**的补 id 追加事务。真实解析（含走树）**< 350 ms**，DOM 创建 599.9 ms。
> 完整订正见下一节「P8-01b」与 `perf/report.md` 的 `## P8-01b` 整节。
> 本节不删，因为「减法漏了一个变量」这个失败形状本身是 P8 的资产。

**做法：不动 `src/` 一行，全部在页内劫持打点。** 四刀：

1. 劫持 `view.updateState`（`original.call(this, state)` 保 `this`，出窗口立刻还原）
   → 把「DOM 创建 + 装饰应用」从 `setContent` 里切出来；
2. 装饰复用 derive 层既有探针（`globalThis.__larkDocPerf` 的 `rebuild` 样本）
   → **DOM 创建（净）= updateState − 装饰**；
3. 同一篇文档换 JSON 灌入做一轮 → **解析 = HTML 轮 − JSON 轮**；
4. 事务段 = 残差。闭包 `解析 + 事务 + updateState = setContent` 由脚本自己断言。

| 文件 | 性质 | 内容 |
| --- | --- | --- |
| `scripts/perf/attribute.mjs` | 新增，约 560 行 | 四段测量（分项 / 规模曲线 / 按块类型 / 分段灌入），分段跑互不覆盖（`measuredSections` / `carriedSections`） |
| `scripts/perf/browser.mjs` | 新增，106 行 | 从 `measure.mjs` 抽出的共享环境（`findChromium` / `serveStatic` / `prepareHostPage` / 负载门），两个脚本共用一套，避免归因结果与门禁口径分叉 |
| `scripts/perf/build-doc.mjs` | 修改 | 抽出 `buildDocBlocks()` 返回顶层块数组（`buildDocHtml` 仍是 `join('')`，逐字节不变）—— 分段灌入要按**顶层块**切，字符串切会把 `<td><p>` 误判 |
| `scripts/perf/measure.mjs` | 修改 | 改为引用 `browser.mjs`，删掉本地三个环境函数 |
| `perf/report.md` | 新增小节 | 「P8-01：那 35 秒花在哪」，含分项表、口径说明、规模曲线、按块类型、分段灌入否证 |

**结果（2,000 块 / 2,478 顶层元素 / 212.8 KB / 16,525 节点）：**

| 分项 | 耗时 | 占比 |
| --- | ---: | ---: |
| Run A 冷机 `setContent`（与 `mountToTypeableMs` 同构） | 42,084 ms | — |
| 解析（HTML 轮 − JSON 轮，含走树） | **38,376.8 ms** | **97.3%** |
| ├ 原生 `DOMParser` 单独量（参考） | 9.2 ms | 0.02% |
| 事务（残差） | 98.7 ms | 0.3% |
| `view.updateState`（1 次） | 713.8 ms | 1.8% |
| ├ 装饰计算 | 113.9 ms | 0.3% |
| └ DOM 创建（净） | 599.9 ms | 1.5% |
| 首次 layout + `focus` | 261.1 ms | 0.7% |

**四条结论（都已写进 `perf/report.md`，含每条的反证）：**

1. **决策点判「是」，但成分错了**：DOM 创建 + 解析 = 98.8%，占大头的却是 HTML 走树解析
   （97.3%），「一次性建 DOM」只有 599.9 ms。**慢的不是浏览器**：同一个 212.8 KB 字符串
   `DOMParser` 只要 9.2 ms，相差 4,000 倍以上 —— 成本在 ProseMirror `parseHTML` 规则匹配 + 节点构造。
2. **它是二次的**：规模曲线 `144 → 2,478` 块，`µs/节点` 从 192.8 涨到 2,420.4（×12.6），
   log-log 最小二乘 **k = 1.80**。文档翻倍、账单 ×3.5。
3. **按块类型没有杠杆**：`µs/节点` 313~455 基本恒定，「表格贵」只因一块 36 个节点。
   **否掉「先优化表格」**。
4. **方案 A 的原形不是解药**：切 1/5/10/25 段灌入，首段 41,797.6 → **227.4 ms（−99.5%）**，
   但总耗时 ×1.00 / ×1.19 / ×1.48 / **×2.20** 单调变差。300 块独立交叉验证排除热漂移
   （11 秒跑完，同向单调）。它买的是**感知延迟**，不是吞吐。

**两条踩过的坑（都在脚本注释里留了因）：**

- **探针不能污染被测量对象**：`DOMParser` 参考量最初放在测量窗口**之前**，它造出的 21 万节点
  临时文档在 `setContent` 期间被 GC，实测把 Run B 从 ~36 s 抬到 ~45 s（+26%）。移到窗口之后才修好。
- **残差容差必须是软的**：`updateState` 轮间抖动（654~880 ms）与 JSON 轮整轮（812.5 ms）同量级，
  残差正负会随抖动方向翻转。改为 `max(50 ms, 1% × setContent)`，超出仍抛错。

### P8-01b 订正归因：一笔 7,932 步的事务（已完成，未发布）

**结论先写**：P8-01 的「98.8% 是 HTML 走树解析」**是假结论**。真正的成本是一笔
**7,932 条 `setNodeMarkup`** 的追加事务（补 `blockId`），以及被这 7,932 步连累的 `autolink`。
原先那条「解析 = HTML 轮 − JSON 轮」的减法里，两轮差了**两个**变量（解析路径、`blockId` 有无）——
`getJSON()` 的节点自带 `blockId`，JSON 轮**零 fix 事务**，所以那笔事务全被算进了「解析」。
**没有重跑实验就推翻了这个结论，靠的是把它切到插件级。**

**做法：仍然 `src/` 一行未动，把 P8-01 的三刀加到四刀。**

1. `view.updateState`（实例方法）→ DOM 创建 + 装饰应用（沿用 P8-01）；
2. **`Object.getPrototypeOf(editor.state).applyTransaction`** —— 必须钩原型：Tiptap 的
   `dispatchTransaction` 走 `view.state.applyTransaction(tr)`，**不经过 `view.dispatch`**，
   钩 `dispatch` 会一点都量不到；这一刀同时包住「应用 step」与「插件 `state.apply`」；
3. **每个插件的 `spec.state.apply` / `spec.appendTransaction`** —— 能这样改是因为
   `EditorState.apply()` 遍历 `config.fields` 时存的是 `spec.state` **对象本身**（不是副本），
   而 `appendTransaction` 每次事务现读 `plugin.spec`；
4. **读 `applyTransaction` 的返回值 `result.transactions`**，取每条的 `steps.length` ——
   追加事务走 `applyInner`、不经过 `applyTransaction` 钩子，步数只能从返回值里拿。
   **这一列是本轮唯一的硬证据。**

**屏蔽实验（只验证归属，不是产品口径）**：页内把 `plugin.spec.appendTransaction` 置 `null`
（ProseMirror 是裸真值判断 `if (plugin.spec.appendTransaction)`，`node_modules/prosemirror-state/dist/index.js:804`），
不改源码、不重建编辑器。

**四条实测（2,000 块 / 2,478 顶层元素 / 载荷门 7.19~7.57）：**

| 场景 | `setContent` | 事务净额 | `larkDoc$` | `autolink$` | 相对基线 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线 | 34,543.1 ms | 33,469.2 | 12,454.3 | 18,572.2 | ×1.00 |
| 摘 `autolink` | 19,803.8 ms | 18,390.9 | 15,228.6 | — | −42.7% |
| **摘 `larkDoc`** | **963.1 ms** | 31.1 | — | **14.8** | **−97.2%** |
| 两个都摘 | 1,466.5 ms | 2.7 | — | — | −95.8% |

1. **钱在事务里，不在 `updateState`**：300 块切 10 段逐次回归，增量斜率 `+39.3 ms/100 块` 中
   事务净额 `+35.0`（**89%**）、装饰 `+3.2`（8%）、`updateState` `+1.2`（3%）、解析 `−0.1`（≈0）。
   DOM 创建几乎不涨 —— 直接否掉「DOM 创建是二次的」。
2. **主导项是补 `blockId`，不是 `autolink`**：摘 `larkDoc` 回收 97.2%，摘 `autolink` 只回收 42.7%。
   摘掉 `larkDoc` 后 `autolink` 从 18,572.2 ms 掉到 **14.8 ms（−99.9%）** —— 它本身在这篇文档上
   几乎免费，机制是 `combineTransactionSteps(oldState.doc, [...transactions])` 把整批 step
   **在新文档上重放一遍**，再 `getChangedRanges` 遍历。**步数是它的乘数**，它是「被连累的」。
3. **步数与块数严格线性，每步成本随文档上升**：619 块 → 1,941 步；2,478 块 → 7,932 步
   （×4.09 / 顶层元素 ×4.00）。而每步成本 0.61 → 1.99 ms（×3.26）：一条 `setNodeMarkup`
   要把 Fragment 里到该位置之前的孩子重新过一遍，位置越靠后越贵 →
   「n 条 step」×「每条约 O(n)」= **Θ(n²)**。两个乘数叠加就是 P8-01 量到的 `k = 1.80`。
4. **去掉平方项后接近线性**：619 块 273.6 ms → 2,478 块 1,466.5 ms，规模 ×4.0 / 账单 ×5.36，
   **k = 1.20**。这就是「A/B 候选」的收益天花板：**两个数量级**。

**一条必须说清的口径**：屏蔽实验表取 `probe-2000-c1.json`（load 7.19，`setContent` 34,543.1）；
步数表的每步成本跨了两次采集（500 块 load 8.97 / 2,000 块 load **10.48**，后者 `setContent` 43,705.8）。
按负载比 1.17 把 2,000 那轮折回 ≈ 37,355 ms，仍比 500 轮的线性外推（3,516.7 × 4.0 = 14,067 ms）
高 **×2.65** —— **Θ(n²) 不是负载造出来的**。而两轮测到的追加步数（1,941 / 7,932）与负载无关，
是这一节唯一不需要打折的硬证据。

**为什么只有挂载/大段粘贴会卡**：`setContent(HTML)` 全 2,000 块缺 id → 7,932 步 → 34.5 s；
`setContent(JSON)`（`getJSON()` 回灌）节点自带 id → **0 步** → ~812.5 ms；日常回车分段只 1~2 步 → 亚毫秒。

**一条踩过的坑（写在报告里）**：屏蔽轮 `focus('start')` 出现过 **77,670.9 ms** —— 被屏蔽后文档
**缺 `blockId`（非法状态）** 把 focus 路径拖坏了，属实验副作用。该列在屏蔽轮不可读，不参与任何结论。
