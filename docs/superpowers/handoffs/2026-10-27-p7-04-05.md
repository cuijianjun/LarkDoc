`vitest.config.js` 强制 `environment: 'node'`，**没有 DOM、没有 rAF**。所以：

## 5. 验收判据与 P7-05 决策（大概率是「不做」）

当前实测（`perf/.perf-result.json`，`capturedAt 2026-10-27T10:30`，即 P7-01 之后）：

| 指标 | 值 | 备注 |
|---|---|---|
| `mountToTypeableMs` | 39232.7 | 基线 59849.7 → 只降 34%，**不是数量级** |
| `keystrokeP95Ms` | 6002.1 | Task 5 的核心靶子 |
| `decorationsRebuildMs` | 2.1 | 基线 21186.3 → **已被 P7-01 打平** |
| `scrollFps` | 59.3 | **> 40，已达标** |
| `saveProxyMs` | 25 | |
| `heapMB` | 107.4 | |

结论与含义：

- **滚动已经不是问题（59.3 FPS）**，计划 Step 4 的「scroll < 40 FPS」条件不成立。P7-05 的 `content-visibility` 只在 `mountToTypeableMs` / 键击仍不达标时才考虑，而它治的是**绘制**、不治 `setContent` 的建 DOM。
- 计划原文写的是「或」条件，但用户口径是**能不做就不做**。所以 Task 5 的交付里 P7-05 大概率写成**「不实现窗口化 / 不加 content-visibility」的理由**，落 `docs/guide/performance.md`，而不是真去改 CSS。真要做，必须同时验 Ctrl+F、打印、选区、屏幕阅读器 DOM、≥50 FPS —— 这个成本很高，先量出 keying 的瓶颈在哪再决定。
- **`perf/baseline.json` 仍然是失真的**（`decorationsRebuildMs 21186.3`、`scrollFps 3.7`）：3.7 FPS 是探针未预热导致的假值（`db125b4` 已修），21 秒是 P7-01 之前的数。**重采要等用户点头**（`node scripts/perf/report.mjs --update`），不要擅自覆盖——会丢掉 before 数。
