# 7. 发布

> 返回[开发导航](./00-INDEX.md)。只接入 SDK 的开发者不需要执行本文命令。

## 先合入 master

先在修复分支完成测试和审查，将确认的改动提交并合入本地 `master`，再从 `master` 发布。脚本不替你切分支、合并或解决冲突，发布前应检查工作区、待提交文件和远端分支。不要覆盖已有 npm 版本或移动旧标签。

在仓库根目录运行：

```bash
npm run ship -- --dry-run          # 先查看计划
npm run ship                      # 默认升级 patch，校验并发布
npm run ship:minor                # 升级 minor
npm run ship -- --version <未发布的新版本>  # 使用已准备的明确版本
npm run sync -- -m "fix: 说明"    # 只提交并推 GitHub，不改版本、不发 npm
```

`ship`、`release`、`release:patch` 都调用 `scripts/release.sh`。脚本清除注入的 `NODE_OPTIONS`；网络命令使用官方 registry，避免本机代理配置干扰。认证未完成时通过 npm 官方登录流程恢复，不在仓库保存密码或验证码。

## 脚本做什么

| 阶段 | 内容 |
| --- | --- |
| 预检和版本 | 确认 master、运行时、远端与 npm 登录，拒绝已占用版本和标签；同步核对 package 与 lock 的根版本 |
| 验证 | 现代 Node 执行 `check:gate`，Node 14 执行 `check:artifacts`；日志保留在 `.release/` |
| 公开出包 | 默认调用 `scripts/pack-sdk.mjs`，保留由宿主共享的 external 运行依赖，检查 tgz 版本、入口和本地哈希 |
| npm 发布 | 对已验证的**公开 tgz 文件本身**执行 `npm publish`，发布为 `latest`，不重新打源码目录；GET 线上 tgz 并比较 SHA1 |
| Git 同步 | 提交发布版本信息，创建 `v<版本>` 标签，正常推送 master 与标签；不强推 |

库兼容构建使用 Node 14.21.3；发布与测试使用现代 Node/npm。默认从 `$HOME/.nvm` 查找 Node 14.21.3 和 Node 24.22.0，可使用 `LARK_DOC_NODE14_DIR`、`LARK_DOC_NODE24_DIR` 指向本机对应的 `bin` 目录，无需使用某位维护者的个人路径。独立出包命令见[仓库开发入口](../DEVELOPMENT.md)。

公开 `0.14.6` 保持 external 运行依赖和已有宿主共享 Yjs 的接法。完全离线包使用 `pack:sdk` 的 `--intranet-version 0.14.6-intranet.1` 选项单独生成，包含普通编辑及 `collabDependencies` 所需的完整运行依赖，并只在暂存目录处理 Webpack4 兼容性；完整命令见[仓库开发入口](../DEVELOPMENT.md)。`release.sh` 默认不生成或发布这个独立内网版本。

普通 `npm pack lark-doc@0.14.6` 不能作为完全离线包。内网归档须保留仅通过 peer 引入的依赖，**不要对已完成的自包含 tgz 再执行 `npm pack`**，否则可能裁掉这些包。

源码目录的 `prepublishOnly` 会阻止直接 `npm publish`。手工发布只用于已完成相同门禁、独立审查、版本与 SHA 校验的公开 tgz；例如 `npm publish /绝对路径/lark-doc-0.14.6.tgz --registry=https://registry.npmjs.org/ --tag latest`。不要使用另一份未验证的包替换它。

## 失败后继续

任一步失败即停止。`.release/pending-version` 保存本次版本，处理原因后可运行：

```bash
npm run ship -- --resume
```

显式版本可以等于已准备的源码版本；包版本、锁文件根版本、`dist/lark-doc-manifest.json` 和最终 tgz 必须一致，不能仅改版本再复用旧 manifest。已发布版本不会被重复发布；若 npm 已成功而 Git 同步失败，先核对线上包，再只完成缺少的 Git 操作。

`--skip-check` 只用于同一份源码、版本和产物已经通过门禁的情况；`--skip-publish` 不发 npm，`--skip-git` 不提交推送，`--include-new` 会把未跟踪文件纳入提交。使用前查看 `npm run ship -- --help` 并审查文件范围，不能用这些开关绕过发布验收。

registry 的即时 `npm view` 或 tarball HEAD 可能尚未同步，成功标准是 GET 下载的包与本地最终 tgz 哈希一致，并确认 `latest` 指向目标版本。

## 文档和在线 demo

版本变更与上线状态统一维护在[开发手册](../DEVELOPMENT.md#release-history)：开发完成先写“未发布”，发布前确认该版本实际包含的新增、修复、兼容变化和提交；各渠道成功后再填写日期、标签、验证结果及 npm/内网交付/文档/Demo 状态。仅本地提交或部分渠道成功时保留对应状态，不提前标记为全部上线。不要为每次发布再创建一份报告文件。

发布时同步 README、接入页面、最小应用的 SDK 版本及锁文件。GitHub Pages 从 master 构建库、同步 `docs/public/demo/vendor/`、构建六个环境示例，再使用 Node 20 构建文档站；生成的 vendor 不手工提交旧二进制。

验收包括 Pages workflow 成功、页面显示目标版本、六类图表实际 SVG、服务器上传/返回地址渲染与完整回调。GitHub Pages 只托管静态页面，图片服务器仍由调用者配置。Windows 离线安装和 Linux 文档部署的命令集中在[内网接入](../docs/guide/intranet-migration.md)；历史测试记录不能当作新版本通过的证据。
