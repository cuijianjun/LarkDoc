# 分支与合并策略

> 2026-10-29 建线。此前是「next/0.12 上直接开发 + 一堆 worktree 各挂一条分支」，
> 结果 next/0.12 与 master 分叉 155:10，AI 适配层在 master 上躺了很久没进主线。
> 现在收口成：**master 只收 dev，dev 只收 feature 分支**。

## 三条分支

| 分支 | 角色 | 能不能直接改 |
| --- | --- | --- |
| `master` | 发布线。只接收 dev 的合入，代表"已稳定" | 不能直接开发 |
| `dev` | 集成分支。所有功能先到这里，稳定后整体合 master | 不直接改代码，只做合并 |
| `feature/<主题>` | 功能分支。从 dev 切，做完合回 dev | 随便改 |

`next/0.12` 保留不动：它是 dev 的祖先，历史提交都在里面，但**不再是开发线**。

## 日常操作

切功能分支（推荐带独立检出，避免和主检出的构建互相踩 webpack 缓存）：

```bash
git branch feature/<主题> dev
git worktree add /Users/cjjxw/codex/.wt-larkdoc/<主题> feature/<主题>
cd /Users/cjjxw/codex/.wt-larkdoc/<主题>
ln -s <主检出>/node_modules node_modules     # 新检出没有依赖，必须软链
ln -s <主检出>/dist dist
```

做完后合回 dev（**用 `--no-ff`**，保留功能分支的形状，便于整条回滚）：

```bash
cd <dev 检出>
git merge --no-ff feature/<主题>
```

dev 稳定后合 master：

```bash
git checkout master && git merge --no-ff dev
```

## 提交写法（都是踩过的坑）

| 规则 | 说明 |
| --- | --- |
| 禁止 `git add -A` / `git add .` | 必须 `git add -- <pathspec>` 精确暂存，否则会把别人骑在工作区的改动一起提交 |
| 普通提交：`git commit -F - -- <pathspec>` | heredoc 写正文，pathspec 限定范围 |
| **合并提交不带 pathspec** | `git commit -- <pathspec> -F -` 会报 `pathspec '-F' did not match`；解决冲突后用 `git add -- <file>` 逐个暂存，再 `git commit -F -` |
| 推送带 IPv4 | `GIT_SSH_COMMAND="ssh -4" git push origin <branch>` |
| 动 tag 前先 `git ls-remote --tags origin` | 远端有而本地没有的 tag，推的时候才会发现 |

## 环境陷阱（会让人误判门禁结果）

1. **新 worktree 没有 `node_modules` / `dist`**，需软链到主检出。软链后两者共用
   `node_modules/.cache/webpack`，会出现「构建成功但产物是旧包」——改完 src 要验指纹
   （在 `dist/lark-doc-element.umd.min.js` 里 grep 新加的断言文案）或看 stat 时间。
2. **`_codex/` 整个被 `.gitignore` 排除，但 `_codex/gen-contract.mjs` 是 `npm run contract:check`
   的依赖**。于是**任何新 worktree 都跑不了契约门禁**，报 `Cannot find module`。
   临时办法：从主检出拷一份过去（该脚本零本地依赖，可直接拷）。
   待办：把三个生成脚本（`gen-contract.mjs` / `split-req.mjs` / `gen-req-index.mjs`）
   加 gitignore 例外或移进 `scripts/`，让它们入库。
3. **`ps aux` 在本 shell 被拒**（operation not permitted）。查负载用 `sysctl -n vm.loadavg`。
4. **shell 的 `grep -rn` 递归有时静默返回空**（不报错、直接没输出）。用 Grep 工具代替，
   否则会把"没搜到"误判成"代码里没有"。
5. 机器 16 核但 load 长期 6~9，性能采集的合格判据是 `max(4, cores×0.5)` = 8；
   `npm run build:element` 会把 load 推到 15，所以"要不要重跑构建"要想清楚。

## 门禁

| 命令 | 覆盖 | 耗时 |
| --- | --- | --- |
| `npm run check:quick` | architecture + contract + lint | 秒级～分钟级 |
| `npm run check:code` | check:lark-doc（含 check-ai）+ architecture + 单测 | 慢（单测 1681 例约 8 分钟） |
| `npm run check:ui` | 主题 token + 对比度 | 快 |
| `npm run check` | 全量（含构建与体积） | 最慢 |
| `npm run check:perf` | 构建 + 采集 + 基线判定 | 最慢，需要空闲机器 |

按改动域挑门禁，别每次跑全量 —— 对照表见 [`01`](./01-环境与校验链.md)。
